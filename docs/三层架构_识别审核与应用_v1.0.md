## 一、先复审现有图像识别插件

### 1.1 现在实际有什么

现有工作区不是单个提示词，而是一套可审计流水线：

- 任务调度：任务.py 的 new / next / submit / status / check / review / import / finalize；
- 识别片段：raw.json 由脚本落盘，Agent 只交片段；
- 问题账本：issues.json；看不清进 uncertain，不猜；
- 审核：task_review.xlsx（审核总览 / 问题清单 / 待审核数据 / 文件归档清单）；
- 人工决定：decisions.json 是权威，Excel 只是派生；
- 输出：final.xlsx（明细数据 + 成分事实）、导出长表.py、收尾报告.py；
- 表型：schemas/*.json；样板确认后注册，后续按契约走；
- 防错：原文对账、合计校验、row_role、归档计划、断点续跑、并行防卡死。

示例任务 20990101_001 实测：3 张图、12 行、2 种表、4 个问题、8 个成分行。

### 1.2 原有审核层的优点

1. 数据安全：不猜、不造数、原文对账；问题全部记账。
2. 可追溯：raw/issues/decisions/final 分层，能追到问题编号。
3. 断点续跑：每张图提交即落盘，失败不丢。
4. 有裁判：validate_export.py 统一生成问题和审核表，避免各脚本口径不同。
5. 表型契约：同一版式只做一次样板，后续批量走。

### 1.3 原有审核层的真实缺口（为什么要第二层）

1. 审核只能在 Excel 里做：问题清单是一张平表，看不到原图与表格的对应关系；审核员要来回切窗口。
2. 不能自由修订：Excel 审核主要填员工决定，任意字段/成分的修订没有统一入口；改原文后成分不能联动。
3. 所有表被压成一张 49 列宽表：六个工作表混在一起，列名取并集，审核时很难定位。
4. 审核与输出绑死：默认走 task_review → decisions → final.xlsx；没有“只审、只出几张 Excel、不建库”的独立模式。
5. 没有独立接口：审核工具不是 HTTP 服务，Agent/其他系统无法在审核完成后取结果；也没有供第三层直接消费的 reviewed 数据。
6. 人工介入点太少：现在主要是最后一次性复核；样板确认和问题决定之间没有连续的“人可随时接管”的界面。
7. MCP/插件边界未定：当前是 DSH 技能 + Python 脚本；MCP 还是后续包装，不是现有实现。

结论：底层流水线是对的，不应推倒；缺的是第二层独立审核台和明确的三层契约。

## 二、三层架构

~~~text
┌─────────────────────────────────────────────────────────────┐
│ 第一层：Agent / 插件 / 技能 / MCP                            │
│                                                             │
│  图片 → 视觉模型 → 识别片段 → raw.json + issues.json          │
│  样板确认 / 表型注册 / 批量转录 / 断点续跑                     │
│  人工可介入：确认样板、补充规则、处理看不清的图                 │
└──────────────────────────┬──────────────────────────────────┘
                           │ 文件契约：runs/<run_id>/
                           │ raw.json + issues.json + source/ + schemas
                           ▼
┌─────────────────────────────────────────────────────────────┐
│ 第二层：识别审核台 review_web（本轮新建）                     │
│                                                             │
│  左图右表：原图 / 每张表 tab / 单元格编辑 / 问题卡             │
│  人工修订：字段、成分、row_role、问题决定、备注                │
│  输出：reviewed.json + 审核结果_<run>.xlsx + decisions.json   │
│  不连数据库；可选给第三层                                     │
└──────────────────────────┬──────────────────────────────────┘
                           │ 文件/JSON 契约：reviewed.json
                           │ 或按 sheet 映射成 /api/ingestions
                           ▼
┌─────────────────────────────────────────────────────────────┐
│ 第三层：Python 数据应用 br-app                                │
│                                                             │
│  面板 CRUD / 成分查询 / 条件查询 / 来料分析 / 综合报表          │
│  长期存储 + 检索 + 分析；也可只做“导入后分析”                 │
└─────────────────────────────────────────────────────────────┘
~~~

### 2.1 为什么拆三层

- 有的部门只要“识别 + 人审 + 两三张 Excel”，不需要建库、不需要长期检索；第二层单独就能交付。
- 有的部门需要长期分析、条件查询、报表，才把 reviewed.json 推进第三层。
- 第一层换模型、换插件、换 MCP，不影响第二层审核界面。
- 第三层换数据库/换分析逻辑，不反过来绑死识别流水线。
- 每层都可以人工接管；AI 负责跑腿，人负责拍板。

### 2.2 层间契约

| 边界 | 输入 | 输出 | 不做什么 |
|---|---|---|---|
| L1 → L2 | 图片、raw.json、issues.json、source/、schemas | runs/<run_id>/ 完整目录 | 不写数据库；不替人做决定 |
| L2 → L3 | reviewed.json（行、字段、成分、问题决定、统计） | 可选导入 payload / Excel | 不长期存储；不改 raw |
| L3 → 用户 | 面板、查询、分析、报表 | Excel/页面 | 不回头改审核状态 |

第二层不读取第三层的数据库；第三层也不读取 raw.json。唯一的桥是 reviewed.json 或适配后的导入 payload。

## 三、第二层：识别审核台（本轮交付）

### 3.1 使用方式

双击 02_图像识别 根目录的 打开审核页.bat，或：

~~~bat
cd C:\Users\<用户名>\Desktop\数据系统开发\02_图像识别
python -m review_web.server --run 20990101_001
~~~

浏览器打开 http://127.0.0.1:8770/。

### 3.2 页面结构

- 顶部：任务选择、图片/行/问题/待处理/阻塞行统计、保存、导出。
- 左：原图；缩放、适应窗口、新窗口打开。
- 中：按工作表 tab 的表格；单元格直接编辑；问题格黄色、已处理绿色；下方显示选中行的成分编辑和不确定项。
- 右：问题清单；候选 A/B 一键采用、自定义值、通过、备注；待处理/全部筛选。
- 保存：review_state.json；导出：reviewed.json + 审核结果_<run>.xlsx。

### 3.3 输入/输出

输入：

~~~text
runs/<run_id>/
├─ raw.json       # 图片 + 行 + 字段 + 成分 + uncertain
├─ issues.json    # 问题账本
└─ source/        # 原图
~~~

输出：

~~~text
runs/<run_id>/
├─ review_state.json                 # 本工具权威审核状态
├─ decisions.json                    # 兼容旧审核脚本
├─ reviewed.json                     # 第三层/其他系统标准交接
└─ 审核结果_<run_id>.xlsx             # 审核总览/问题/按表/成分长表/原图
~~~

### 3.4 审核规则

- 问题候选：可以点 A/B 直接采用，也可以输入任意修正值；
- “通过”只表示接受原识别值，不修改字段；
- 行内任意字段可直接编辑；直接编辑会写 row_overrides，不改 raw.json；
- 成分可增删改名和原文值；长表按修订后的成分输出；
- 只有 warn/error 未解决才阻塞行；info（如表型未注册）只提示、不阻塞；导出时仍会保留“待处理”状态，提醒不要直接交付；
- 人工决定和字段修订都写 reviewed.json，可追溯。

### 3.5 明确不做

- 不建数据库、不做长期检索；
- 不自动归档原图（仍交给原 validate_export.py / 收尾脚本）；
- 不自动推第三层（本轮只产出 reviewed.json；适配器下一步做）；
- 不自动合并重复成分、不自动改 raw.json；
- 不做登录/权限（本机预览）。

## 四、AI 全流程怎么跑（每一步可人工干预）

~~~text
1. 用户放图 → Agent 建任务
2. Agent 做样板 → 人确认表型/列/一行代表什么
3. Agent 批量识别 → 每张落盘 → 问题进 issues.json
4. Agent 打开审核台 → 人看图/改表/点问题候选
5. 人点导出 → reviewed.json + Excel
6. 需要长期分析 → 第三层导入 reviewed；不需要 → Excel 直接交付
~~~

人工介入点：

- 样板确认：L1 阶段，决定表型；
- 看不清：L1 阶段进 uncertain；L2 阶段人填；
- 审核修订：L2 阶段，任意字段/成分/问题；
- 是否入库：L3 入口，由人决定；
- 任何一步 Agent 都不能绕过人直接写正式账。

### 4.1 Agent 如何调用第二层

- 本地：Agent 运行 python -m review_web.server，把 URL 交给用户；
- HTTP：第二层已有 /api/runs、/api/run、/api/save、/api/export，未来可包成 MCP 工具；
- 文件：Agent 只要保证 runs/<run_id>/raw.json + issues.json + source 齐全，第二层就能独立启动。

### 4.2 第三层怎么接

已接通一条最小链路：

~~~bat
cd C:\Users\<用户名>\Desktop\数据系统开发\03_数据系统开发\03_原型与代码\br-app
python manage.py import_reviewed --reviewed C:\...\reviewed.json --dry-run
python manage.py import_reviewed --reviewed C:\...\reviewed.json
~~~

- 映射：seeds/reviewed_maps.json；先做“库存明细 → br_inventory”；
- 只收 status=ok 的行；blocked 默认跳过；
- 生成 L3 待审核草稿，不直接写正式记录；人工确认后才入库；
- 同一 reviewed 文件重复执行返回原批次，不重复建账。

其余表示例：来料分析类 → incoming_analysis，其他库存/分析表 → 对应面板；需要逐张补映射和验收。适配器不放在第二层，避免第二层绑死 L3 面板。

## 五、对第一层的复审结论与建议

保留：

- raw.json / issues.json / decisions.json / final.xlsx 分层的审计思路；
- 原文对账、row_role、不能猜、断点续跑、样板契约；
- validate_export.py 作为唯一裁判。

改造：

1. 第二层不再生成/依赖 task_review.xlsx；Excel 只作为输出，不作为审核入口。
2. raw.json 不改；审核修订写 review_state.json / reviewed.json。
3. issues.json 仍是唯一问题源；第二层只加人工决定，不另造问题。
4. 把“审核完成”从 Excel 导入改为 reviewed.json 导出，减少一次手抄。
5. 逐步把 task_review.xlsx 的问题清单/待审核数据降级为兼容输出，而不是主流程。

不建议：

- 不要把三层合成一个 Django 项目；
- 不要让第二层直接写数据库；
- 不要为了自动化跳过人工审核；
- 不要在没有 reviewed.json 契约前做 MCP 全自动。
