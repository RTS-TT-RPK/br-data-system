## 1. reviewed 文档 v2（L2 → L3）

### 1.1 顶层结构

```json
{
  "schema_version": "reviewed/v2",
  "authority": "L2 review_state + row_overrides",
  "run_id": "20990101_001",
  "reviewed_at": "2026-10-28T20:00:00",
  "deliverability": {
    "status": "deliverable",
    "deliverable": true,
    "blocking_issues": 0,
    "info_issues": 2,
    "blocked_rows": 0,
    "stale_decisions": 0,
    "revision_errors": 0,
    "reasons": []
  },
  "source": {
    "workspace": "C:/Users/<用户名>/Desktop/数据系统开发/02_图像识别",
    "created": "2026-10-28 20:00:00",
    "raw_sha256": "64位十六进制",
    "raw_run_id": "20990101_001"
  },
  "stats": { "images": 3, "rows": 12, "sheets": 2, "issues": 4,
             "blocking_issues": 0, "info_issues": 2, "resolved_issues": 0,
             "blocked_rows": 0, "components": 8 },
  "images": [ { "image_id": "...", "file": "runs/.../source/x.jpg", "sha256": "...",
                "sheet_label": "...", "date_text": "...", "url": "/source?..." } ],
  "sheets": [ { "name": "库存明细", "columns": ["库位"], "row_count": 2 } ],
  "rows": [ /* 见 1.2 */ ],
  "issues": [ /* 见 1.3 */ ],
  "decisions": { "issue_decisions": {}, "row_overrides": {}, "archive_decisions": {} },
  "archive_plan": {}
}
```

- `status` 只有两个合法值：`"deliverable"`（可交付）与 `"draft"`（审核中、不可交付）。
- `deliverable` 必须与 `status` 一致；`reasons` 在 draft 时必须给出人能看懂的原因（中文）。
- 只有 `deliverable=true` 的文件允许被 L3 作为正式导入来源。
- 旧格式 `reviewed/v1` 继续可读（L3 dry-run 只读预览），但**不能作为正式导入**；L3 必须给出明确错误。

### 1.2 rows[] 行对象

除 reviewed/v1 已有字段外，v2 增加/明确：

```json
{
  "row_id": "R075",
  "image_id": "测试7",
  "sheet": "库存明细",
  "row_role": "data",
  "object_label": "THF-杂-低",
  "required_fields": [],
  "fields": { "库位": "示例库区3#", "成分明细": "THF79.9% 水11% PH8" },
  "components": [ /* 见 1.2.1 */ ],
  "uncertain": [],
  "status": "ok",                       // 必填，只允许 "ok" / "blocked"；缺失即非法
  "raw_hash": "64位十六进制"             // 该行 raw.json 内容哈希（见 2.1）
}
```

#### 1.2.1 components[] 成分对象（A 工作包的核心）

```json
{
  "name": "乙酸",
  "raw_value": "5%",          // **有效原文值**：人工修订后为人工值，否则为原识别值
  "value": "0.005",             // **有效规范值**：字符串十进制；% 时为 0.005
  "unit": "%",
  "recognized": {               // 原识别值；**未被人修订时为 null**
    "raw_value": "5%",
    "value": "0.05",
    "unit": "%"
  },
  "from_human": true,           // 是否有人工修订
  "field": "成分明细",           // 该成分来自哪一列（可选）
  "revision_error": null        // 非空字符串表示人工输入无法安全解析，该行必须 blocked
}
```

规则：
1. 人工修订**不得覆盖原识别值**：`recognized` 保存原值，`raw_value/value` 是当前有效值。
2. `value` 与 `raw_value` 必须自洽（用 L3 解析口径换算后相等）。
3. L3 导入**只使用有效值**（raw_value/value/unit），不再优先取原始 value。
4. 宽表字段（如 `fields["成分明细"]`）与 `components` 由同一份有效数据生成，不得两套数。
5. 人工输入无法解析时：该行 `status="blocked"`，并在 `revision_error` 与 issues 中留下可读原因；**不得静默沿用旧值**。

### 1.3 issues[] 问题对象

保留 v1 字段，新增：

```json
{
  "issue_id": "ISS-OCR-R001-乙酸",
  "type": "OCR_UNCERTAIN",
  "severity": "warn",
  "field": "乙酸",
  "target_ids": ["R001"],
  "candidates": ["0.5%", "5%"],
  "decision": "",
  "note": "",
  "resolved": false,
  "blocking": true,
  "needs_reconfirm": true,          // 旧决定绑定的是另一版内容，必须重新确认
  "stale_decision": {               // needs_reconfirm=true 时保留旧决定供追查
    "decision": "0.5%",
    "note": "",
    "reason": "该行内容已变化（raw 行哈希不一致）"
  }
}
```

- `severity=info` 的问题永不阻塞交付，只做提示。
- 未解决（resolved=false）且 blocking=true 的问题 → 文件只能 draft。

## 2. 人工决定的内容绑定（B 工作包）

### 2.1 规范化哈希（L1 与 L2 必须完全一致）

**行内容哈希** `canonical_row_hash(row)`：

1. 取字段子集（缺失按 null）：`row_id, image_id, sheet, row_role, object_label, fields, components, uncertain, 拆开`。
2. `components`：每个成分只取 `{name, raw_value, value, unit}`（多出的键丢弃）；`uncertain`：每项只取 `{field, candidates, note}`。
3. `json.dumps(obj, ensure_ascii=False, sort_keys=True, separators=(",", ":"))` → UTF-8 → sha256 hex。

**问题内容指纹** `canonical_issue_fingerprint(issue)`：

1. 取子集：`{issue_id, type, field, target_ids(字符串并排序), candidates(保持顺序), description}`。
2. 同样 JSON 规范化 → sha256 hex。

**证据对象 `evidence`**（写进 decisions.json 的每条 issue_decisions / review_state 中）：

```json
{
  "run_id": "20990101_001",
  "raw_sha256": "raw.json 的 sha256",
  "issue_fingerprint": "……",
  "row_hashes": { "R001": "……" }
}
```

- `row_hashes` 覆盖该问题的所有 `target_ids`。
- 决定记录字段：`{issue_id, decision, note, evidence}`；可附带 `history: [旧记录…]`。
- **兼容**：没有 `evidence` 的旧决定按 legacy 处理（照旧可用，但显示“旧格式，未绑定内容版本”）。
- **失效判定（L1/L2 必须一致）**：`needs_reconfirm` 当且仅当
  ① `evidence.run_id` 与当前 run 不一致；或
  ② `evidence.issue_fingerprint` 与当前问题指纹不一致；或
  ③ 该问题任一 `target_ids` 行的当前 `canonical_row_hash` 与 `evidence.row_hashes` 不一致（行已不存在也算不一致）。
  `raw_sha256` 只作整份来源溯源与审计（写入 reviewed/v2 的 source），**单独不一致不判 stale**；
  否则重识别任意一张图会让全任务旧决定一起失效，与“对应的旧决定重新确认”不符。
- 失效的决定**不得自动套用**：该问题保持阻塞，旧决定/旧备注/原因保留在 `stale_decision` 与 `history` 中，等人工显式重新确认。

### 2.2 run 身份

- `decisions.json` / `review_state.json` 顶层必须有 `run_id`。
- 读取方（L1 / L2）发现 run_id 与当前 run 不一致 → **整份拒绝套用**并明确说明；不得按 issue_id 硬套。
- L2 `save_state` 必须保持 `run_id` 与当前 run 一致；旧 decisions.json（无 run_id）按 legacy 兼容但给出警告。

### 2.3 重新确认语义（L2 save API）

- `POST /api/save` 请求体新增可选：
  - `reconfirmed: ["issue_id", …]`：用户显式重新确认了这些旧决定 → 服务端用**当前内容**重算 evidence。
  - `retouched_rows: ["R001", …]`：用户在当前版本上重新编辑了这些行 → 服务端更新该行 override 的 `_base_row_hash`。
- 未出现在上述列表、且 evidence 已失效的决定/行修订：服务端**保留旧 evidence 与旧值**（继续 needs_reconfirm），不得静默重新绑定。
- 行修订在 state 中的写法：`row_overrides[row_id] = {fields, components, row_role, deleted, uncertain, _base_row_hash}`。
  `_base_row_hash` 与当前行哈希不一致 → 该行修订**不应用**，行 blocked 且提示“人工修订所基于的行内容已变化，需重新确认”。

## 3. L3 reviewed 导入校验（D 工作包）

L3 适配器（`panels/services/review_import.py`）在创建草稿前必须逐项检查；任一失败 → 停止并给出中文可读错误（不创建批次、不写记录）：

1. **版本**：`schema_version == "reviewed/v2"` 才允许正式导入；`reviewed/v1` → 仅 dry-run 预览，正式导入报错“旧格式，请用 L2 重新导出 v2”；未知版本 → 报错。
2. **身份**：`run_id` 非空；`source` 为对象且 `source.raw_sha256` 为 64 位十六进制；缺失 → 报错。
3. **交付状态**：正式导入要求 `deliverability.deliverable == true` 且 `status == "deliverable"`；draft → 报错并列出 reasons。dry-run 允许 draft，但必须打印“不可交付”原因。
4. **行状态**：每行 `status` 必须是 `"ok"` 或 `"blocked"`；缺失/其他值 → 报错（**不能把缺状态当 ok**）。
5. **行号**：同一 sheet 内 `row_id` 不得重复；重复 → 报错。
6. **工作表和映射**：只处理映射里声明的工作表；未映射工作表的行计数并报告“不导入”，不视为错误。
7. **字段**：映射 `fields` 引用的源字段必须存在于行 `fields`（允许为空字符串，但键须存在）；映射可声明 `required` 源字段列表，缺失或空 → 报错。
8. **单位**：成分 unit 必须在映射 `allowed_component_units`（默认 `["%", "‰", "ppm", "mg/L", "g/L", "", "—"]`）；否则报错。
9. **数值一致**：每个成分用 `raw_value`（必要时拼 name）按 L3 解析口径解析出的数值，必须与 `value` 相等（相对误差 ≤ 1e-6）；不一致 → 报错（防止 5% 与 0.05 混用）。
10. **文本一致**：若行里同时有成分原文列（`component_source`）和 `components`，把原文拆成“成分型 token”后与 components 按 (名称, 规范数值) 多重集比较；不一致 → 报错。
11. **声明一致**：`deliverability.blocked_rows` 必须等于实际 `status="blocked"` 行数，否则报错。
12. 通过后：只取 `status="ok"` 的行建 `IngestionBatch(status="pending")` 草稿批次；`IngestionRow.row_key = row_id`；payload 行增加 `source: {run_id, sheet, row_id, image_id}`；**不创建正式 Record**。
13. `--include-blocked` 只在同时给出 `--force-reason` 时允许；批次 note 与审计必须记录“强制包含阻塞行：原因…”，CLI 打印风险提示；这些行明确标为阻塞来源，不得当作正常数据。
14. 审核页保留“去 L2 核对原图”入口：链接到 `settings.REVIEW_WEB_URL + "?run_id=" + batch.source_run_id`。

## 4. L2 服务端 payload（给前端/测试的稳定字段）

`GET /api/run` 返回（在原有基础上新增）：

```json
{
  "deliverability": {
    "deliverable": false, "status": "draft",
    "blocking_issues": 18, "info_issues": 6, "blocked_rows": 16,
    "stale_decisions": 2, "revision_errors": 1,
    "reasons": ["还有 18 条阻塞问题未解决", "还有 16 行处于阻塞状态"]
  },
  "state_warnings": ["decisions.json 属于任务 X，已忽略"],
  "stats": {
    "images": 8, "rows": 86, "all_rows": 86, "sheets": 6, "issues": 25,
    "pending_issues": 24, "blocking_issues": 18, "info_issues": 6,
    "resolved_issues": 1, "blocked_rows": 16, "components": 50,
    "stale_decisions": 2, "issue_progress_pct": 5,
    "deliverable": false
  }
}
```

- `issue_progress_pct` **只按阻塞问题计算**：`已解决阻塞数 / 阻塞问题总数`；阻塞总数为 0 时为 100。
- 问题对象新增 `needs_reconfirm`、`stale_decision`；人工输入解析失败的合成问题 `synthetic=true`、`type="HUMAN_VALUE_INVALID"`、`severity="error"`。
- 行对象新增 `raw_hash`、`component_field`；成分对象见 1.2.1。

`POST /api/export` 请求体：`{run_id, mode: "draft" | "deliverable"}`（缺省按 draft）。

| mode | 前置 | 产物 |
|---|---|---|
| draft | 无 | `审核留档_<run>.xlsx` + `reviewed_draft.json`（醒目“审核中·不可交付”） |
| deliverable | deliverable=true | `审核结果_<run>.xlsx` + `reviewed.json`（标“可交付”） |

- deliverable 不满足时返回 HTTP 409，`{ok:false, error, deliverability:{...reasons}}`；不得生成任何文件。
- 两种模式都先按 1.2 生成同一套数据，再套文件头/文件名。

## 5. 外接硬盘备份（E 工作包）

### 5.1 配置（JSON，非数据库；默认 `br-app/data/backup_config.json`，测试用 setting 覆盖）

```json
{
  "target_dir": "E:/BR备份",
  "confirmed_external": true,
  "auto_daily": true,
  "l1_workspace": "C:/Users/<用户名>/Desktop/数据系统开发/02_图像识别",
  "last": {
    "result": "success",            // success | failed | not_configured
    "at": "2099-01-01T00:00:00",
    "target": "E:/BR备份",
    "backup_dir": "E:/BR备份/backup_20990101_000000",
    "error": "",
    "files": 123,
    "bytes": 4567890,
    "db_integrity": "ok"
  }
}
```

- 未配置 target（空）时：状态显示“未配置备份目标，当前没有新备份”，**绝不可显示成功**。

### 5.2 备份内容与清单

时间戳目录 `backup_YYYYMMDD_HHMMSS/`，至少：

1. `db/preview.sqlite3`：用 `sqlite3.Connection.backup` 生成一致快照；先写临时文件→对副本 `PRAGMA integrity_check`→ok 后改成正式文件名。
2. `config/panels_snapshot.json` + `seeds/*.json`（面板与导入映射配置）。
3. `l1/runs/…`（识别结果、人工决定、review_state、reviewed、审核状态、来源图片）、`l1/inbox|pending|archive|golden|schemas`、`l1/aliases.json`、`l1/对照表.json`。
4. `backup_manifest.json`：备份时间、来源范围、目标、文件数量、总字节、数据库检查结果、排除数量与原因、失败信息、每条 scope 的文件数。

排除：`__pycache__`、`*.pyc`、`*.tmp`、`.tmp`、测试数据库（`test_*.sqlite3`）、`.env`/`*.key`/`*.pem`/`credentials*`、`node_modules`、`.git`。

### 5.3 行为

- 只复制，不移动、不改写来源；不删除旧备份；不做恢复；不覆盖 `preview.sqlite3`。
- 目标未配置/盘未接入/不可写/空间不足/快照或校验失败 → 明确失败，保留旧备份；失败状态写进 config.last，页面显示“当前没有新备份”。
- 首次设置必须让用户勾选“我确认这是另一块硬盘”；应用可提示盘符相同但不能断言物理盘。
- 每天第一次启动（首页首次请求）自动尝试一次（fail 后当天不反复重试），也可手动“立即备份”。

## 6. 验收映射（README 对应）

| 工作包 | 关键验收 |
|---|---|
| A | 某成分 5%→0.5%：页面、审核 Excel、reviewed.json、L3 dry-run、L3 草稿均为 0.5%；原识别 5% 可追溯 |
| B | 行内容变化后旧“通过/数值”不自动生效；跨 run 决定文件被拒；L1 旧导出遇 row_overrides 拒绝生成最终文件 |
| C | 1 行阻塞：留档可生成且醒目标“不可交付”；交付导出/正常导入被拒；清零后才可交付；info 不阻塞、进度只按阻塞 |
| D | 有效 v2 示例 dry-run 成功；缺状态/未知版本/错误来源/数值不一致被拒；blocked 行计数跳过；正式库无测试写入 |
| E | 临时目录合成数据全流程；失败路径不谎报成功；旧备份保留；来源未改动；inbox/runs 等真实数据未被测试触碰 |
| G | 缺成分=未知、0 才是零；别名查询结果说明同口径；无有机成分=“无法识别主溶剂”；沸点/共沸提示语保留 |
