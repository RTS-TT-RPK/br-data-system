## 0. 摘要（先看这一页）

### 0.1 一句话目标

做一个**定制版 ERP**：仓储（收料、储罐/仓库库存、出入库、盘点、预警）+ 生产（工艺卡、工单、投料/产出、收率）+ **排产**（塔/罐/班组/交期约束下的生产计划与甘特图）+ 报表；纯 Python、双击即用；**所有能力同时以"人类界面 + Agent 工具（MCP/API）"两种方式暴露**，让 DSH 这类 Agent 能把图片识别出的表格数据直接写入系统，并在授权范围内代替人做数据管理。

### 0.2 与现有 Excel 的关系

- **继承**：物料/共沸/储位/罐型液位标定这 4 张基础数据、55 条隐含业务规则（体积/重量/价格/共沸/工艺卡字段等）、12 个操作入口背后的业务动作、用户熟悉的表单+表格+导出习惯、操作日志思想。
- **不继承**：VBA、Excel 作为数据库、COS/JSON 同步、秒级时间戳事件、1:1 照搬界面、任何测试业务数据。
- **补上 Excel 没有的**：订单/供应商/客户、库位容量与预留、盘点、质量/批次、生产工单、**排产计划**、附件/图片、API/MCP、权限与审计、备份恢复。

### 0.3 推荐技术路线

```
┌──────────────────────────── 一台厂内电脑 / 也可单机 ────────────────────────────┐
│  启动器（一键启动/备份/恢复/升级/开关 Agent）                                     │
│      ├─ Web 应用：Django 5.2 + SQLite(WAL) + HTMX（人用界面）                      │
│      ├─ REST API：/api/v1（OpenAPI 文档，Agent 与外部系统用）                      │
│      ├─ MCP Server：把领域能力暴露成工具给 DSH/Claude 等 Agent 调用                │
│      ├─ 文件/图片接入：inbox 目录 + ingestion API（识别结果→校验→审核→入库）        │
│      └─ 附件库：图片/单据按 SHA256 存证，可追溯                                    │
└──────────────────────────────────────────────────────────────────────────────────┘
```

- 语言/框架：Python 3.13 + Django 5.2 LTS + Django Ninja（或 DRF）+ SQLite（WAL）+ HTMX/Bootstrap；排产 v2 可加 OR-Tools CP-SAT；MCP 用官方 `mcp` Python SDK（FastMCP）。
- 交付：便携文件夹 + 内置 Python 运行时 + 桌面快捷方式（v2.0 设计），双击即用，不装 Python/Office。
- 联网：**默认只在本机**，但 API/MCP 从第一天就按"可联网"设计（token、版本、幂等、限流、审计）；局域网/远程/Tailscale 作为开关，不在 v1 承诺。

### 0.4 范围分三期（按"可验收"重排，不按功能数量）

| 期 | 内容 | 人日（AI 辅助） | 日历（每周 3–4 天） |
|---|---|---|---|
| **一期：账务闭环** | 主数据 + 仓储（收货/入库/移库/出库/盘点/预留/预警）+ 生产批次（投料/产出/质量/追溯）+ 基础报表 + 权限/审计 + 一键启动/备份恢复 | 55–95 | 14–24 周 |
| **二期：可视化排产** | 订单/设备/罐容/日历建模 + 甘特图 + 人工排程 + 冲突检测 + 规则排序 + 历史回放验证 | +15–30 | +4–7 周 |
| **三期：受控 Agent** | REST/OpenAPI 只读→草稿→人工确认→提交 + 图片识别草稿试点 + 幂等/限额/审计/回放 | +15–30 | +4–7 周 |
| **合计（可用版）** | | **85–155 人日**（含 20% 缓冲 102–186） | **约 6–11 个月**（每周 3–4 天；全职约 4–7 个月） |

> 关键改动：**一期先证明"库存账 = 生产消耗/产出账"能对上**，而不是先做排产和 Agent。排产二期先用"甘特图 + 人工拖 + 冲突提示 + 简单规则"验证价值，确认能改善人工计划后才考虑求解器；Agent 三期先只读、再草稿、最后才试点受控提交。

### 0.5 开工前需要确认的 7 个架构级问题（详见 §13）

这些答案决定架构，而不仅是界面：

1. **终端数**：现在 1 台？2–5 台？5 台以上/多班组？（决定本机还是局域网服务器模式）
2. **生产模式**：主要是间歇批次、连续，还是混合？（决定排产/工单/罐区模型）
3. **排产痛点**：人工排产够用只想减少记录？经常换料/罐容/交期冲突？还是尚未量化、不确定值不值得自动化？
4. **Agent 权限**：只读分析？可生成草稿、人确认？还是允许低风险操作自动提交？（默认只到"草稿+人确认"）
5. **网络**：必须离线？需要局域网多人？还是先本机、以后可扩展？（默认本机+局域网开关）
6. **开发投入**：接近全职？兼职 + AI？还是多人协作？（决定工期区间与里程碑粒度）
7. **成本核算**：只做数量与生产记录？要批次成本/收率/毛利分析？还是要完整成本与财务报表？

## 1. 产品定位、用户与边界

### 1.1 产品定位

**定制版轻量 ERP**，不是通用 ERP，不追求财务总账/税务/人事，只做这家废溶剂回收企业最核心的"料、罐、塔、单、产、排"：

| 板块 | 内容 | 优先级 |
|---|---|---|
| 基础数据 | 物料（含混合物/别名）、共沸、储位、罐型与液位标定、塔、班组、供应商/客户、单位、工艺配方 | P0 |
| 仓储 | 收货（袋/桶/罐车）、入库、储罐液位、仓库货位、移库、出库、盘点、预留、低库存/高液位预警 | P0 |
| 生产 | 一期：生产批次记账（投料/产出/收率/批次追溯）；二期：完整工单执行（开工/暂停/完工/停机） | 批次记账 P0；完整执行 P1（见 §1.6） |
| 排产 | 订单池、产能/日历、排产计划（甘特）、冲突检测、发布、实际对比 | P1（MVP-2） |
| 报表 | 库存台账、收发存、产量/收率、排产执行率、成本/利润（后期） | P1 |
| Agent | API、MCP、图片/单据接入、审核队列、操作回放 | P2（MVP-3，但接口从 MVP-1 就留） |
| 系统 | 账号/角色/审计、备份恢复、一键启动、升级、日志 | P0 |

### 1.2 用户与使用场景

| 角色 | 主要动作 | 终端 |
|---|---|---|
| 仓库/罐区管理员 | 收料、入库、移库、出库、盘点、看液位/库容 | 车间电脑/平板浏览器 |
| 车间班长/操作工 | 领料、投料、生产记录、报异常 | 车间平板/电脑 |
| 生产计划员 | 建订单、排产、调整甘特、发布计划、跟踪执行 | 办公室电脑 |
| 老板/管理者 | 看库存、产量、排产、异常、利润（后期） | 手机/电脑（可选外网） |
| **AI Agent（DSH 等）** | 调用 MCP/API：查库存、建草稿、提交识别数据、建议排产、执行授权操作 | 本机（通过 DSH 插件/MCP） |

### 1.3 本期范围与"明确不做"

**一期（账务闭环）做**：
- 主数据（物料/别名/共沸/储位/罐型标定/供应商/客户/塔/班组/字典）与导入。
- 仓储全流程：收货（磅单/化验单）→入库→移库→出库→盘点→预留→预警；批次/质量状态参与可用量判断。
- 生产批次：投料、产出（主产品/副产物/残液/损耗）、收率、班组、停机；批次与库存流水双向追溯。
- 基础报表：库存台账/收发存/产量/收率/账实差异；Excel 导出。
- 系统：权限/审计/一键启动/备份恢复/升级；库存-生产人工对账。
- 对外：REST/OpenAPI 只读接口骨架（为三期留），不建完整 MCP。

**二期（排产）做**：甘特图、人工排程、冲突检测、简单规则排序、计划版本、历史回放对比；**先证明比人工强，再谈优化器**。

**三期（Agent）做**：REST 只读 → 业务草稿 → 人工确认 → 提交；图片识别结果接入草稿/审核；幂等、限额、审计、回放。

**明确不做（避免范围失控）**：
1. 一期不做 CP-SAT/复杂多目标优化；
2. 一期不做 Agent 自主执行正式库存过账；
3. 一期不同时建完整 MCP 工具体系与两套业务实现（REST 优先，MCP 薄适配）；
4. 不做云部署/多租户/跨厂协同（只留字段与抽象）；
5. 不做复杂成本核算/财务报表，除非被确认为当前决策刚需；
6. 不为"表数量"提前建无真实业务支撑的实体；
7. 不做移动 App、完整质量管理体系、公网门户。

### 1.4 "成功"的可量化标准

| 维度 | 标准 |
|---|---|
| 仓储 | 收/发/存/移/盘全流程可追溯；库存账实可对（账面 vs 盘点差异有原因）；储罐液位→体积误差 ≤ 标定精度；预警可用 |
| 生产 | 每批投料/产出/收率可查；工单与库存联动；损耗可解释 |
| 排产 | 能按约束生成可执行计划；冲突能提示；计划 vs 实际有偏差分析；排产时间从"半天 Excel"降到 ≤10 分钟 |
| Agent | DSH 能从图片提取表格 → 调用工具 → 生成待审核草稿 → 人确认后入库；全过程有审计；重复提交不重复入库 |
| 一键 | 干净 Windows 双击即用；备份/恢复/升级可用；断外网不影响 |
| 可维护 | 一人 + AI 能改字段/加规则；有测试；文档三件套 |

### 1.5 关键假设（评审时可反驳）

- H1：单厂区、3–8 个并发用户、东八区；排产以"天/班"为粒度，不要求分钟级。
- H2：塔数量有限（现有工艺卡里出现 1、3、新1、新4 等），可枚举；塔的工艺能力可人工配置。
- H3：订单来源以"收废料（收处置费）+ 产成品销售"为主，排产目标可先按"交期优先 + 毛利优先"组合权重。
- H4：图片识别由外部 Agent/插件完成，本系统只负责"结构化结果→校验→入库"，不做 OCR 本体。
- H5：默认单机/局域网；外网只读可后加，不影响主架构。
- H6：基础数据沿用现有 4 张表；其余业务数据不迁。
- H7：文字/单据格式会变，import profile 必须可配置，不能把所有字段写死在代码里。

## 2. 从 Excel 继承什么、不继承什么

### 2.1 继承（参考价值）

| 继承项 | 用途 |
|---|---|
| 物料性质 4 条（15 字段：CAS/沸点/密度/闪点/GHS/价格…） | 主数据、安全信息、密度/价格计算 |
| 共沸数据 3 组 | 混料/配伍预警、工艺风险提示 |
| 储存位置 4 个（2 仓库位 + 2 罐位）+ 罐型 10 种 + 液位-体积 12×10 | 仓储模型、液位换算 |
| 55 条隐含规则（见 v1.0 §5） | 重量/总价/共沸/工艺卡/日志等业务正确性 |
| 12 个操作入口的业务动作 | 功能清单（不等于界面照抄） |
| 工艺卡 12 字段、生产记录 10 字段 | 生产模块字段基线 |
| 操作日志思想 | 审计基础（但要补操作人/模块/前后值） |
| 用户习惯：表单、表格、筛选、Excel 导出 | UI/交互基线 |

### 2.2 不继承

| 不继承 | 原因 |
|---|---|
| VBA/宏/COM/ODBC | 目标就是彻底去 Excel |
| Excel 作为数据库 | 无约束、无事务、无并发 |
| COS/JSON 事件同步 | 当前数据问题的根源；改为中心库/单机库 |
| 秒级时间戳当唯一键、先本地后云端双写 | 改为数据库事务 + UUID + 审计 |
| 1:1 照搬 12 个窗体 | 重新设计为 ERP 流程（如"收货→入库→库存"是三步而不是一个窗体） |
| 隐藏工作表手工维护基础数据 | 改为正式维护界面 + 导入模板 |
| 旧业务数据 | 用户确认为测试数据，不迁移 |

### 2.3 Excel 没有、但定制 ERP 必须补的

订单/供应商/客户、收货单与磅单、批次与质量属性、库位容量与预留、盘点、移库、生产工单、排产计划/甘特、日历/班次、塔能力与清理切换矩阵、API/MCP、附件、权限、审计、备份、升级。

## 3. 总体架构

### 3.1 系统上下文

```
  人（仓库/车间/计划/老板）          AI Agent（DSH、Claude 等）           外部文件
        │ 浏览器                        │ MCP / REST API                    │ 图片/Excel/CSV
        ▼                              ▼                                   ▼
┌─────────────────────────────────────────────────────────────────────────────────┐
│                          BR ERP 核心（Python / Django）                          │
│  表现层：Web 页面（HTMX）   │   接口层：REST /api/v1（OpenAPI）+ MCP Server     │
```

### 3.2 分层与依赖方向

| 层 | 内容 | 规则 |
|---|---|---|
| 领域层 `domain/` | 计量换算、库存规则、排产算法、共沸/价格、状态机 | **不依赖 Django、不依赖数据库**；纯函数 + 数据类型；可单独 pytest |
| 应用层 `services/` | 用例：收货、入库、移库、出库、盘点、建工单、排产、提交识别结果 | 事务边界；编排领域层与仓储层；权限检查入口 |
| 接口层 `api/` `mcp/` | REST、OpenAPI、MCP 工具、参数校验、错误码、幂等 | 只调应用层；不直接写 SQL；不信任客户端 |
| 表现层 `web/` | Django 视图/模板/HTMX | 只调应用层；不做业务计算 |
| 基础设施 `infra/` | ORM 模型、迁移、附件存储、日志、备份、事件/outbox | 可替换（SQLite→PostgreSQL） |

### 3.3 进程与部署形态

单机/局域网默认部署（与 v2.0 一致）：

```
BR数据系统.exe（启动器，tkinter，无控制台）
  ├─ 检查/迁移数据库
  ├─ 启动 waitress（Django）：127.0.0.1:8765（单机）或 0.0.0.0:8765（局域网）
  ├─ 启动 MCP Server（按需）：stdio 或 127.0.0.1:8766（供 DSH 连接）
  ├─ 启动 inbox 文件监听（按需）：data/inbox/
  └─ 打开浏览器
```

- 服务端始终**单进程写库**（SQLite WAL），不做多 worker；注意 waitress 单进程仍可能由多线程处理请求，**SQLite 写必须串行化**：短事务、BEGIN IMMEDIATE、busy_timeout、冲突重试；排产/报表用只读快照，不在事务内跑长计算；并发写明显增加或需要多进程时，评估 PostgreSQL。
- MCP Server 是独立进程，通过本机 HTTP（带 token）调用应用层；也可提供 stdio 模式供 DSH 配置。这样"Agent 接入"失败不影响人用界面。
- 未来多终端/远程：把 Web+API 部署到厂内服务器或经 Tailscale，客户端仍是浏览器/Agent，业务代码不变。

### 4.6 关键状态机

```
收货单:   draft → confirmed → received（生成入库流水） → closed
工单:     draft → released → scheduled → in_progress → done / cancelled
排产计划:  draft → published → archived（可复制为新 draft）
识别草稿:  draft → validated → pending_review → committed / rejected
Agent 写操作: propose(draft) → awaiting_confirm → committed / rejected（按自主级别）
```

### 4.7 约束与索引（关键）

- 唯一：物料名、别名、储位编码、罐型+液位、塔编码、工单号、幂等键、图片哈希。
- 外键：库存→储位/物料；流水→库存；工单→订单/配方/塔；排产条→计划/工单/塔。
- 检查：数量/体积/金额非负（除冲正）；液位 0–最大量程；收率 0–1（或 0–100 统一为小数）；日期合理。
- 索引：`stock_movement(item_id, occurred_at)`、`stock_item(location_id,status)`、`schedule_slot(plan_id,tower_id,planned_start)`、`operation_log(occurred_at,module)`、`ingestion(status,created_at)`。
- 余额校验：每日/每次写后校验 `stock_item.volume = Σ volume_delta`，不等则告警并冻结相关操作。

### 4.8 业务事实与状态转换矩阵（评审 C1 的直接回应）

> 目的：先定义"业务事实如何变化"，再决定表怎么建。任何功能开发前，这张表必须逐行确认。

| # | 业务动作 | 前置状态/条件 | 影响的实体 | 库存/生产影响 | 审计与凭证 | 失败回滚 |
|---|---|---|---|---|---|---|
| 1 | 收货登记 | 供应商启用；车/单据信息完整 | 收货单、附件 | 不直接改库存（待检验） | 收货单号、操作人、原图 | 作废收货单 |
| 2 | 检验/放行 | 有化验结果；质量规则 | 批次、质量状态 | 待检→合格/不合格/让步；未放行不可领用 | 检验记录、放行审批人 | 回退质量状态（留痕） |
| 3 | 入库（仓库/储罐） | 放行或免检；储位可用/罐容足够 | 库存余额、库存流水 | +数量/+液位→体积/重量/金额 | 入库流水、单据号、附件 | 冲销流水（红冲） |
| 4 | 冻结/解冻 | 质量或异常处理 | 批次、可用量 | 冻结库存不计入可用量 | 冻结原因、操作人 | 解冻留痕 |
| 5 | 领料/投料 | 工单已开工；物料已放行且可用量足够 | 工单投入、库存余额、流水 | −可用量；生成消耗记录 | 领料单、工单、操作人 | 退料或红冲 |
| 6 | 生产开工 | 工单已排/已下达；罐容/设备可用 | 工单、塔、班组 | 占用设备/罐；不直接改库存（投料时才扣） | 开工记录 | 取消开工（回退状态） |
| 7 | 生产暂停/恢复 | 工单进行中 | 工单、停机记录 | 记录停机时段与原因 | 停机单 | 修正停机记录（留痕） |
| 8 | 完工 | 投料/产出录入完整；质量检验 | 工单、产出批次、库存 | 主产品/副产物/残液入库；损耗核销 | 完工单、产出流水、质量 | 反完工需审批（红冲） |
| 9 | 退料 | 工单存在未用投料 | 工单、库存、流水 | 退回可用库存（质量状态不变） | 退料单 | 红冲 |
| 10 | 移库/倒罐 | 源有量；目标容量足够；物料兼容 | 库存、储位/罐 | 源−目标+；记录混合/成分变化 | 移库单 | 反向移库 |
| 11 | 盘点 | 生成账面快照；停止相关收发 | 盘点单、库存 | 盘盈/盘亏生成独立调整凭证 | 盘点单、差异原因、审批 | 反向调整（红冲） |
| 12 | 出库/销售 | 客户/合同；可用量足够；质量放行 | 出库单、库存、流水 | −库存；金额/毛利归属 | 出库单、附件、操作人 | 红冲/退货 |
| 13 | 冲销/红冲 | 原凭证存在且未结账 | 原单据、库存/生产 | 生成反向流水；不物理删除 | 红冲单关联原单 | 不可撤销则作废红冲 |
| 14 | 质量降级/让步 | 检验不合格但可降级使用 | 批次、质量状态、价格 | 可用量/用途受限；成本口径变化 | 审批记录 | 恢复需重新审批 |
| 15 | 计划发布/冻结 | 排产计划校验通过 | 计划、工单 | 不直接改库存；冻结期内不允许随意移动 | 发布记录、版本号 | 取消发布（保留版本） |

**规则**：跨实体动作必须在一个事务内完成（如"完工→产出入库→工单关闭"）；跨天的动作（检验→放行）用状态机而非事务；任何红冲/反审必须留痕且可追溯到原凭证。

#### 4.8.1 逐动作可执行规格（评审 C4 的直接回应：开发前必须逐项填完）

每个业务动作必须补齐 10 个字段，缺一项不得开发：**前置状态 → 触发条件 → 事务边界 → 生成凭证 → 计量维度变化（主计量/体积/重量/金额）→ 质量/批次变化 → 反向动作 → 审批要求 → 重复提交处理 → 下游已使用时的处理**。

评审点名的 5 处歧义，先明确如下：

| 场景 | 明确规定 |
|---|---|
| 预留/领料/投料的时点 | 订单"下达"时建立预留（占可用量，不生成流水）；仓库存量"领料"生成库存流水；车间"投料"生成工单消耗记录（实际耗用）；退料生成反向流水；工单完工/取消时释放剩余预留。**预留 ≠ 流水 ≠ 消耗**，三者分表、分状态。 |
| 待检产出的入库 | 工单"完工"时产出先入"待检库存"（quality=pending，不增加可用量）；检验合格→"放行"转为可用；不合格→隔离/返工/降级（走审批）；只有放行后才可销售/领用。产出不能因"完工"直接变为可用。 |
| 混罐/倒罐 | 倒罐产生**新批次**（新 lot_no），记录来源批次与比例（未知比例则标"成分不明"）；质量状态重新判定；原批次按移出量扣减直至关闭；不允许把不同质量状态/不相容物料无审批混合。 |
| 红冲与下游已使用 | 若原库存已被领用、转移、生产消耗或销售：**禁止直接反向流水**；必须走受控反转链（审批 + 补偿凭证 + 必要时通知财务）；红冲不得造成负库存；原凭证与反向凭证双向关联，历史链路可解释。 |
| 部分收货/部分完工/返工/盘点冻结/取消已发布计划 | 部分收货：留待收数量、生成部分入库；部分完工：允许分批产出、工单保持进行中；返工：新工单引用原批次；盘点冻结：冻结期内禁止收发，差异审批后生成调整凭证；取消已发布计划：保留版本、释放预留、通知车间，不删除历史。 |

> 这张表最终要由业务负责人逐行签字；签字版作为开发规格的一部分，不允许开发者自行解释。

### 4.9 数据不变量与写入规则（评审 C1/I2/I4/I7 的直接回应）

> 每条不变量在开发规格中必须标注：**数据库约束 / 事务策略 / 服务层校验 / 测试编号**，不能只写"服务层保证"。

| 编号 | 不变量/规则 | 落地方式 |
|---|---|---|
| INV-1a | **主计量余额 = Σ 主计量流水**（按库存条目/批次/质量状态） | 每个企业先定义"主计量维度"：仓库按件/桶/吨（物料单位），储罐按液位（测量）→体积（换算）；流水保存 before/after；余额只由服务层事务更新 |
| INV-1b | **派生维度不独立记账** | 体积/重量/金额由主计量 + 换算快照计算：重量=体积×密度快照；金额=重量/数量×价格快照；每次变动保存换算来源（密度、温度、标定版本、价格版本） |
| INV-1c | **不同单位/不同物料/不同质量状态不得直接相加** | 报表按主计量单位分组；跨单位汇总必须显式换算并标注口径；库存条目必须带 unit_id 与 quality_status |
| INV-1d | **液位不是数量** | level_m 仅对储罐有效，是测量值；体积由 tank_calibration(version) 换算；液位不能跨储位相加 |
| INV-2 | **可用量 = 余额 − 预留 − 冻结/待检** | 预留独立表/状态；领料/出库前原子校验；预留有过期、释放、部分释放规则 |
| INV-3 | **禁止直接改余额** | 变动只走单据/流水；盘点差异走调整凭证；修正走红冲 |
| INV-4 | **禁止负库存** | 事务内校验 + 行版本/写锁；并发 retry；失败返回明确错误；测试覆盖并发扣减 |
| INV-5 | **批次/质量门禁** | 仅"放行"批次可领用/出库；待检/冻结/不合格不计可用量；质量状态变更需审批 |
| INV-6 | **幂等** | 写接口必带 Idempotency-Key（作用域=操作类型+业务键，TTL 24h）；DB 唯一索引兜底 |
| INV-7 | **乐观锁** | 余额/单据带 version；提交校验，冲突返回刷新重试；不静默覆盖 |
| INV-8 | **唯一约束** | 单号、批次号、图片哈希、幂等键、业务键 DB 级唯一（不能只在应用层查重） |
| INV-9 | **事务短小** | 排产/报表只读快照；写事务只做必要更新；不在事务内跑长计算；SQLite 写用 BEGIN IMMEDIATE + busy_timeout + 重试 |
| INV-10 | **红冲不删除** | 业务单据不可物理删除；红冲生成反向记录并保留原记录；下游已使用时必须走受控反转（§4.8.1） |
| INV-11 | **作用域** | 业务表带 org/site/warehouse 作用域字段，所有查询/唯一约束/审计都带作用域 |
| INV-12 | **保留策略** | 按记录类别配置保存期限，由企业负责人/财务/档案/合规确认；系统只执行批准策略并记录删除留痕 |

### 4.10 批次、质量、作用域与保留（评审 I5/Q17/Q18 的直接回应）

- **批次/质量字段**：\`lot_no\`、\`quality_status\`（待检/合格/不合格/让步/冻结）、\`composition_text\`、\`source\`、\`disposal_destination\`、\`supplier_id/customer_id\`、\`production_batch_id\`。
- **可用性判定**：库存条目是否可领用 = 质量状态合格 + 未被预留 + 未冻结 + 未过期（如有时效）。
- **追溯链**：成品批次 → 工单 → 投料批次/供应商 → 收货单/原图；销售出库 → 成品批次 → 工单。任何一环可反查。
- **保留期限**：业务记录、原始单据图片、识别原始结果、人工修改记录、审计日志、备份**分别配置**；10 年/3 年等只能作为待讨论草案，**最终由企业负责人会同财务/档案/法务确认**，系统只执行批准后的策略并记录删除/销毁留痕（评审 I6）。
- **作用域**：默认单组织/单厂/单仓；表结构预留 \`org_id/site_id\`，配置分层（全局/站点/实例）；附件路径与编号规则抽象，未来多厂/多租户不推倒重来。

### 4.11 计量维度与换算凭证（评审 C1 的直接回应）

**核心结论：库存不能只用"体积"一个不变量；必须按业务定义主计量维度，其余维度是带换算凭证的派生值。**

| 概念 | 规则 |
|---|---|
| 主计量维度 | 每个库存条目必须有一个主计量：仓库按物料单位（件/桶/袋/吨），储罐按液位（测量值）；由 measurement_policy 配置，不允许同一物料在不同储位任意混用 |
| 体积/重量/金额 | 均为派生或实测值：储罐体积=液位×标定表版本；重量=体积×密度快照（或磅单实测）；金额=数量×价格快照；三者都要保存 before/after 与换算引用 |
| 单位换算表 | 新增 unit_conversion（物料, 从单位, 到单位, 系数, 生效日期, 来源/依据）；没有配置换算的物料禁止跨单位汇总 |
| 密度记录 | 新增 density_record（物料, 密度, 温度, 来源, 有效日期, 版本）；每次变动记录使用的密度版本；主数据改密度不影响历史 |
| 标定版本 | tank_calibration 带 version；每次体积换算记录版本；标定更新不回溯历史体积 |
| 重量来源 | 磅单净重（实测）与体积×密度（计算）都保存；差异超过阈值时以合同/业务口径为准并挂异常；不允许静默二选一 |
| 报表口径 | 按主计量单位分组；跨维度汇总必须显式标注换算口径与版本；禁止把不同单位直接相加 |

新增表：unit_conversion、density_record、measurement_policy；stock_item/stock_movement 增加 primary_unit_id/primary_qty/conversion_ref 字段。

## 5. 业务规则与核心算法

### 5.1 仓储业务规则

| 业务 | 规则 |
|---|---|
| 收货 | 收货单（供应商/车号/毛重/皮重/净重/物料/储位/处置费/化验）→ 确认后生成"入库流水"; 净重与化验结果不一致时挂异常 |
| 入库 | 支持仓库（件/桶/吨）与储罐（液位/体积/重量）两种；储罐入库必须给出液位或体积，按标定表换算 |
| 出库 | 不能超过可用库存（余额−预留）；储罐出库到 0 时关闭记录而不是物理删除 |
| 移库 | 源/目标储位、数量或液位；罐间移库可能产生混合，需记录成分变化 |
| 盘点 | 生成账面快照 → 实盘 → 差异（盘盈/盘亏）→ 审批 → 调整流水（带原因） |
| 预留 | 工单/订单可预留库存；预留不减少账面，但减少"可用量" |
| 预警 | 低库存（按物料/货位）、高液位（>90%）、超期、质量异常；可配置阈值 |
| 批次/质量 | 物料批次号、质量状态（合格/待检/不合格/让步）；不合格库存不可用于生产 |
| 账实一致 | 每日校验余额=流水合计；盘点差异必须闭环 |

### 5.2 计量与价格规则（从 Excel 继承 + 修正）

1. 仓库"数量"=体积（m³）；储罐"数量/液位"=液位（m）；单位在字段与界面显式标注，禁止混用。
2. 重量(t) = 体积(m³) × 密度(g/mL)；总价(元) = 体积 × 密度 × 单价(元/t)；金额存整数分。
3. 储罐体积：按 `(tank_type, level)` 查标定表；默认精确匹配，可选线性插值；越界/缺口拒绝并提示（不得静默 0）。
4. 价格：物料表存"区间文本 + 下限 + 上限"；生效价默认取下限，口径可配置（min/mid/max/手工）；界面显示当前口径。
5. 未匹配物料/密度/价格：阻断保存并提示补主数据（修正旧系统静默算 0）。
6. 共沸预警：仅性质=原料/再加工时；成分按"、"拆分，取百分号前名称（不能用"第一个数字前"）；"无稳定共沸"不预警；别名归一。
7. 舍入：体积/重量 0.001，金额到分；统一在领域层做，不让界面各自 round。
8. 时间：业务时间（进料时段等）与系统时间分开存储；所有写入带操作人/来源。

**5.2.1 计价依据（评审 C2 的直接回应）**

| 交易类型 | 计价依据 | 必存快照 |
|---|---|---|
| 收废料/处置费 | 合同 + 磅单净重（或按车/按桶，以合同为准） | 净重、单价、处置费率、合同号、价格有效期 |
| 产品销售 | 合同/报价 + 出库重量或体积（以合同口径为准） | 数量/重量、单价、币种、税率口径、价格版本 |
| 内部成本/转库 | 加权平均或标准成本（由财务确认） | 成本单价、计算口径、生效日期 |
| 运费/其他 | 单据金额 | 金额、发票/收据号 |

**5.2.2 价格与金额快照（不可回溯改写）**

- 每张正式单据必须保存：price_basis（净重/体积/合同价/手工价）、unit_price_cents、price_source、price_effective_date、使用的价格区间上下限。
- 主数据价格更新**不得**改写历史单据金额；历史金额以单据快照为准。
- 价格区间默认取下限只是"默认策略"，必须可通过配置改为中值/上限/合同价；界面显示当前口径。
- 同一物料不同供应商/客户可以有不同价格，价格不是物料主数据的唯一属性。

**5.2.3 55 条规则逐条处置（开发前置）**

在 M0 阶段建立《规则处置表》：每条规则填 继承/修正/废弃/待确认、理由、影响字段、测试编号、业务负责人签字。未处置的规则不得进入开发；"继承"也必须绑定测试用例。

### 5.3 排产问题定义（v1 可解释模型）

**输入**
- 订单池：待处理订单（类型、物料、数量、交期、优先级、预期毛利、工艺要求）。
- 配方：每个订单/产品对应的 recipe（塔兼容、批次上下限、周期、收率、参数）。
- 资源：塔（能力、可用日历）、班组（可选）、储罐（容量、当前库存、可接收物料）、公用工程（蒸汽/电，可选）。
- 切换规则：recipe → recipe 的清理时间/成本矩阵。
- 日历：班次、检修、节假日。

**决策**
- 每个工单分配到哪座塔、排在第几位、计划开始/结束时间。

**约束**
- C1 塔能力兼容（recipe.tower_compat）。
- C2 同一塔同一时刻只能一个工单。
- C3 必须在工作班次/可用日历内。
- C4 储罐容量：任意时刻原料/中间/产品罐不超容；物料兼容（避免污染）。
- C5 切换清理：不同 recipe 相邻需要清理时间（changeover matrix）。
- C6 批次量上下限/最小批量。
- C7 交期/优先级（软约束，违反产生惩罚）。
- C8 班组可用（可选）。
- C9 公用工程上限（可选）。

**目标（默认词典序，评审 I3 的直接回应）**

1. **硬约束可行**：质量放行、设备适用、罐容/安全、班次/检修、批次上下限——不可违反，违反即不可行。
2. **逾期最小**：按订单交期违约小时/次数排序（先保证交期）。
3. **切换/清洗与空闲最小**：减少换塔、清洗、等待。
4. **毛利/利用率**：仅作为前几项相同时的 tie-break 或人工选择的比较项。

> 加权求和只有在指标定义、归一化方式和业务权重经用户书面确认后才使用；不允许把"小时、元、次数"直接相加。



**输出**
- 甘特计划（每塔的工单序列与时间）；
- 冲突清单（哪些约束被违反、严重度）；
- 每个排产决策的"解释"（为什么排这里/为什么等待）；
- KPI（准时率、利用率、切换次数、预计毛利、罐容峰值）；
- 可手工锁定/拖动调整，再校验。

**参数来源与可信度（评审 C2 的直接回应）**

在写排产代码前，必须先填完这张表；算法只能使用"有来源"的参数，经验值要标注"待校准"：

| 参数 | 来源 | 维护人 | 更新频率 | 验证方式 | 可信度 |
|---|---|---|---|---|---|
| 塔能力/处理量 | 设备铭牌 + 历史实际 | 生产/设备 | 季度或大修后 | 过去 3–6 个月实际批次对比 | 待实测 |
| 单批周期/时长 | 历史工单实际起止 | 生产 | 每月 | 偏差分布（P50/P90） | 待实测 |
| 收率（主产品/副产物/残液） | 历史批次质量/产量记录 | 生产/技术 | 每批更新 | 与化验/计量对比 | 待实测 |
| 物料兼容/可加工性 | 工艺规程 + 技术确认 | 技术 | 变更时 | 小试/历史异常 | 待确认 |
| 切换清理时间/成本 | SOP + 实际记录 | 生产 | 变更时 | 实际停机记录 | 待实测 |
| 罐容/最高液位 | 标定表 | 设备/计量 | 校准后 | 标定表版本 | 高 |
| 质量放行/冻结规则 | 质量规程 | 质量 | 变更时 | 检验记录 | 待确认 |
| 交期/优先级 | 订单/合同 | 销售/计划 | 每单 | 客户确认 | 高 |
| 延误/违约成本 | 业务约定 | 管理层 | 年度 | 财务口径 | 待确认 |
| 公用工程上限 | 设备/能源 | 设备 | 变更时 | 实际峰值 | 待实测 |

> 规则：**没有来源的参数只能用于"建议"，不能用于"自动发布计划"**；每个参数在系统中记录 owner、版本、生效日与校准记录。

**硬约束优先于优化目标**：合规、质量放行、设备适用性、罐容/安全库存、班次/检修、批次最小/最大量属于不可违反的硬约束；交期、毛利、利用率是软目标，违反要显式记录代价，不允许算法"为了利润违反硬约束"。

**评审补充的约束（v3.0 未覆盖）**：
- 设备适用性（某些塔不能加工某些物料/浓度）；
- 质量检验放行时间（待检批次不能排入投料）；
- 原料可用时间（在途/未放行/他单预留）；
- 批次拆分规则（整批不可拆 vs 可拆最小批量）；
- 生产时长不确定性（用 P50/P90 或缓冲时间，而不是固定值）；
- 在制品占罐（中间馏分/过渡罐容量）；
- 停机检修与清洗占用；
- 计划冻结期（已发布计划的近期部分不允许随意改动）；
- 订单优先级/插单规则与违约代价。

### 5.4 排产算法 v1（先可用、可解释、可人工干预）

```
1. 预处理：订单按优先级/交期/毛利排序；生成候选工单（拆批：按 recipe 最小/最大批量）。
2. 初始化：按"交期最早优先 + 同物料合并"分配到兼容塔的空档。
3. 贪心插入：对每个工单，在目标塔的可用时间轴上找最早可行起点；
   逐项检查 C1–C6；插入后更新罐容曲线与塔占用。
4. 局部改进：对相邻工单做"交换/前移"尝试，若目标函数下降则接受（有限迭代）。
5. 冲突处理：无法插入的工单进入"未排池"，给出原因（能力/罐容/交期）。
6. 生成解释与 KPI；保存为 schedule_plan（draft）。
7. 人工可在甘特图上锁定/拖动，系统重新校验并提示冲突。
8. 发布（published）→ 工单进入待执行；实际执行回写 actual。
```

- 复杂度：订单量（几十~几百）× 塔数（几座）× 时间粒度（班次/小时），贪心+局部搜索在秒级完成。
- 确定性：同一输入+参数结果可复现（seed 固定），便于对比与审计。
- 可解释：每个 slot 记录"选择理由/被拒原因/约束检查结果"。

**运行与事务规则（评审 Q10 的直接回应）**

- 排产计算在**只读快照**上运行（复制当前库存/订单/设备状态到内存或临时只读库），不持有写事务、不阻塞日常录入。
- 结果先保存为 \`schedule_plan(draft)\`，发布时用**短事务**校验版本与容量后写 \`schedule_slot\`；不在一个事务里跑算法。
- 同一输入 + 同一参数 + 固定随机种子 → 结果可复现；算法版本与参数快照一起存档。
- 无解/超时时返回"未排池"与原因，不返回半成品计划；人工可接手。

**人工案例回放（验收排产是否创造价值）**

在二期开发前/中，必须收集并回放 **≥20 个历史排产案例**（订单、设备状态、罐容、人工计划结果），比较：
- 人工计划 vs 系统建议：交期达成率、换塔/清洗次数、设备利用率、不可执行条数、预计毛利；
- 计划变更次数、紧急插单处理时间、计划员耗时；
- 若系统建议不能稳定优于或持平人工，**不发布自动计划**，只保留甘特图/冲突提示等辅助功能。

### 5.5 排产算法 v2（可选，MVP-2 后期）

- OR-Tools CP-SAT：把上述约束建模为整数规划，支持多目标（加权/字典序）；适合订单多、约束复杂时。
- 做法：先 v1 出初始解，再用 CP-SAT 在时间预算内改进；无解时回退 v1。
- 风险：求解器依赖体积/许可（OR-Tools 开源）、建模调试成本；因此放在 v2，且可关闭。

### 5.6 计划 vs 实际

- 工单实际开始/结束、实际投料/产出、停机、收率 → 与 `schedule_slot` 对比；
- 报表：计划达成率、延迟原因 TOP、切换次数、收率偏差、罐容风险；
- 后续：用历史偏差校准 recipe 周期与收率（v3 可做，先留数据）。

## 6. Agent 集成（本方案的核心差异化）

### 6.1 设计原则

1. **系统是事实源，AI 是操作者/建议者**：Agent 不直接碰数据库，只能调用受控工具。
2. **人机同权同审计**：Agent 的每一次写操作与人一样进审计，标注 actor=agent/tool/model 版本。
3. **默认可撤销**：写操作先落"草稿/待确认"，再提交；可回滚。
4. **最小权限 + 分级自主**：只读 → 建议 → 授权写 → 人工确认高危操作。
5. **接口稳定**：API 版本化、OpenAPI 文档、字段 schema 机器可读；MCP 工具是对外契约。
6. **离线/本地优先**：默认只开本机；联网是开关，不是前提。

### 6.2 四种集成形态

| 形态 | 用途 | 说明 |
|---|---|---|
| **REST API `/api/v1`** | 任何程序/Agent/插件调用 | JSON、OpenAPI、token 鉴权、幂等键、分页、错误码 |
| **MCP Server** | DSH/Claude 等 Agent 直接调用工具 | 官方 SDK；工具入参出参 schema；stdio 或本机 HTTP；权限按 token |
| **inbox 文件投递** | 识别插件/脚本落文件 | `data/inbox/` 放 JSON+图片，系统监听→生成 ingestion 草稿 |
| **Webhook/事件（可选）** | Agent 被动感知变化 | outbox 事件 + 订阅 URL/轮询；默认关闭 |

**接口优先级（评审 Q6/I2 的直接回应）**

- **REST/OpenAPI 是唯一业务契约**：所有业务能力先有 REST 端点与 schema；界面、Agent、外部程序都调同一服务层。
- **MCP 是薄适配层**：只把筛选后的 REST 能力包装成工具，不实现第二套业务逻辑；MCP 在三期才启用，一期只交付 REST/OpenAPI 只读骨架。
- 如果 DSH 能可靠调用 OpenAPI/任意 HTTP 工具，则 MCP 可完全跳过或延后；不把 MCP 当作一期硬依赖。
- 文件投递（inbox）作为可选补充，最终仍走同一 ingestion 服务与校验。

### 6.3 Agent 身份、权限与自主级别

| 级别 | 名称 | 允许 | 典型场景 |
|---|---|---|---|
| L0 | 只读 | 查询/导出/看排产 | "现在甲醇库存多少？" |
| L1 | 建议（默认） | 创建 draft、生成建议、校验，不落业务表 | 图片识别→草稿；排产建议 |
| L2 | 受控草稿写入 | **只能创建/修改草稿，不落正式库存余额**；正式过账仍需 L3 人工确认 | 经授权的数据准备、识别草稿 |
| L3 | 人工确认后提交 | **正式库存过账、质量状态变更、盘点调整、生产开工/完工、计划发布、作废/红冲、主数据修改** | 必须人在界面确认 |
| — | 管理员 | 不开放给 Agent | 人工 |

- 每个 Agent 有独立 token、scopes、autonomy_level、有效期；启动器可一键吊销。
- 写操作按风险分级：提交时校验 token 级别 + 数据范围（如单批数量上限、允许的储位/物料）+ 频率限制。
- **高危操作永远需要人工确认**（confirm_token 由界面生成，一次性、15 分钟、绑定草稿哈希）。

**默认策略与高危清单（评审 C3/Q7 的直接回应）**

- 默认只开 **L1（草稿/建议）**；**L2（直接提交）默认关闭**，只能按工具/数据范围/数量额度逐项开启。
- 以下操作**永远需要人工确认**，不得 L2 自动执行：正式库存过账、盘点调整、质量放行/降级、生产开工/完工、排产发布、单据作废/红冲、主数据修改与删除。
- 自主级别按"工具 + 作用域 + 额度"定义，不只按数字级别；同一 token 可以"查询 L0、收货草稿 L1、小额入库 L2、排产发布 L3"。
- **身份分离**：\`操作主体\`（人/Agent）、\`令牌身份\`、\`发起人\`、\`审批人\`、\`执行人\`分别记录；Agent token 有独立 scopes、过期、撤销与最后使用时间；审批必须有独立账号，不能 Agent 自批。
- **紧急开关**：启动器"断开 AI"立即吊销/停用所有 Agent token，不影响人用系统。

**MVP 硬规则（评审 C3 的直接回应）**

- 一期/二期/三期 MVP 阶段：**所有改变正式库存余额或质量状态的操作，一律人工确认**；L2 不得用于正式过账。
- Agent 可以做的自动化上限：查询、校验、生成草稿、修改草稿、准备单据；不能自行把草稿变成正式业务凭证。
- 若未来确需 L2 自动提交，必须先满足：连续稳定运行 ≥1 个月、有端到端测试、按工具/范围/额度单独书面授权、可一键回滚；且**永远不包含**正式库存过账。

**token 生命周期（评审 I7 的直接回应）**

- 签发：管理员在启动器/系统内创建，记录签发人、所属 Agent、用途、scopes、作用域（org/site/warehouse）、额度、有效期。
- 存储：只保存哈希；明文只在创建时显示一次；界面不反复展示完整 token。
- 轮换：到期前提醒；支持一键轮换；旧 token 立即失效。
- 泄露应急：一键吊销全部 Agent token；审计最近调用；必要时停用 MCP/API。
- 每次调用校验：token 有效 + scope + 作用域 + 额度 + 频率；吊销后立即拒绝。

### 6.4 写操作安全协议（所有 Agent 写操作统一走这套）

```
1) Agent 调 propose_*（或 create_*_draft）
      → 服务端做 schema/权限/业务校验
      → 返回 draft_id + preview（将写什么、影响哪些库存/KPI、校验问题）
2) Agent 调 validate(draft_id)
      → 返回 errors/warnings/duplicate 提示
3) 分级处理：
   L1：只能停在 draft，等人打开界面审核
   L2：只能创建/修改草稿，不能提交正式库存过账
   L3：界面审核 → 生成 confirm_token → Agent 用 token commit（正式过账唯一路径）
4) commit 必须带 Idempotency-Key；重复请求返回同一结果（不重复写）
5) 提交事务：业务表 + 流水 + 审计 + Agent 日志同事务
6) 返回 committed 实体 id + 影响摘要；失败自动回滚
```

**确认凭证（confirm_token）规范（评审 C3 的直接回应）**

- 绑定：草稿 id + **草稿版本哈希** + 业务动作 + 影响范围（org/site/warehouse/物料/数量/金额）+ 审批人 + 一次性 nonce + 过期时间（默认 15 分钟）。
- 一次性使用；提交时服务端校验：token 未被使用、未过期、草稿内容哈希一致、范围一致、审批人有效。
- **审批后任何业务字段变化都使原确认失效**，必须重新审核。
- 审批记录独立保存：谁批、何时、批的哪个版本；不能只存"已确认"。
- 状态三态：**已识别（recognized）→ 已审核（reviewed）→ 已过账（posted）**，界面与审计分别展示；"已识别"不等于"已审核"，"已审核"不等于"已过账"。

**幂等与去重（评审 I5 的直接回应）**：
- 文件级去重：图片 SHA256 只能识别"同一文件"；同一张单据重新拍照/裁剪/压缩后哈希不同，不能只靠哈希。
- 业务级去重：按 document_type + 供应商/客户 + 单据号 + 日期 + 金额/数量做匹配；缺单号时用多字段组合 + 人工确认。
- 疑似重复：命中时**不自动过账**，返回"疑似重复"并关联原单，要求人工选择"关联/新建/忽略"。
- 幂等：Idempotency-Key 唯一约束；重复键返回首次结果。
- 批量：每批最多 N 行（可配置）；超限拒绝或转人工。

**提交时重新校验（不可省略）**

- \`commit\` 必须重新执行：权限/scope、当前状态机、可用库存与罐容、版本号、单据唯一性、限额、重复提交检查；**不信任草稿生成时的校验结果**（库存可能已变化）。
- 校验与写入在同一短事务；任何一步失败整体回滚，返回明确错误码与可修正字段。
- 限额：单次数量/金额、累计数量/金额、影响实体数、调用频率、异常波动阈值；超限转人工确认。
- 幂等键作用域与有效期：\`(操作类型, 业务键, 来源)\`，默认 24h；同一键重复提交返回首次结果，不重复过账。
- 并发：余额/单据 version 校验；冲突返回"请刷新后重试"，禁止静默覆盖。

### 6.5 图片/单据接入流程（DSH 场景，核心）

**目标场景**：DSH 桌面插件识别一张磅单/送货单/生产记录照片 → 提取表格 → 直接写入 ERP（低置信度/异常进人工审核）。

```
① 用户在 DSH 里对图片执行"表格识别"
② 插件/Agent 调用 MCP 工具 ingestion.create_draft：
   {
     "document_type": "weighbridge_receipt",
     "source": {"kind":"image", "filename":"IMG_001.jpg", "sha256":"..."},
     "extractor": {"name":"dsh-table-extract", "version":"1.2"},
     "confidence": 0.93,
     "data": { "supplier":"某药业", "plate_no":"苏K12345",
               "gross_kg": 32560, "tare_kg": 11840, "net_kg": 20720,
               "material_name":"甲醇废液", "date":"2026-10-27", "ticket_no":"BD20261027001" },
     "lines": [ ... ]
   }
③ 服务端：按 document_type 找 ingestion_profile → 字段映射/单位换算/主数据匹配
   → 生成 ingestion(draft) + ingestion_rows（带 confidence、issue）
④ 校验：必填、数值范围、净重=毛重-皮重、物料是否存在、储位是否可用、
   重复单据号/重复图片、罐容是否够、供应商是否启用
⑤ 结果三态：
   - 全部通过 + 置信度≥阈值 → 生成**已识别/待审核**草稿；**正式过账仍需人工确认（L3）**，不允许直接提交（MVP 硬规则）
   - 有警告/低置信度 → 待审核（L1），页面并排显示原图与解析行，人工修改后提交
   - 有错误 → 拒绝并返回错误清单，Agent 可修正重试
⑥ 提交：生成收货单/入库流水（或生产记录）+ 附件关联 + 审计（actor=agent，tool=ingestion.commit，图片哈希）
⑦ 返回：单据号、写入了哪些库存、影响摘要；失败可回滚（按事务/批次）
```

**审核界面**（人用）：左图右表、低置信度红框、字段旁"来源：第 3 行第 2 列"、一键接受/修改/拒绝；批量审核。
**可追溯**：每条业务记录可反查原始图片（attachment_id），审计里保留 raw_json 与最终值。

**不可变识别记录与修改留痕（评审 I8 的直接回应）**

- 保存：原图/原文件（SHA256 内容寻址）、提取器名称与版本、原始解析 JSON、字段置信度、校验结果、人工修改前后值、确认人、提交结果、关联业务单号。
- 置信度只作为"是否需要人工复核"的参考，**不能替代业务校验**，也不能仅凭模型自报置信度直接正式过账。
- 人工修改必须留痕（字段、原值、新值、修改人、时间）；提交后业务单据可反查整条证据链：图片→提取→草稿→修改→审批→业务记录。

### 6.8 Agent 典型任务模板（给 DSH/插件用）

1. **图片入库**：识别 → `ingestion_create_draft` → `ingestion_validate` → 若 warnings 少且置信度高 → 请求人确认或直接 commit（L2）→ 汇报单据号与库存变化。
2. **库存问答**：`inventory_query_stock` / `inventory_get_tank_state` → 用自然语言回答（不写库）。
3. **排产建议**：`production_list_orders` + `schedule_propose_plan` + `schedule_validate_plan` → 输出甘特摘要/冲突/KPI → 人确认后 `schedule_commit_plan`。
4. **异常巡检**：`inventory_list_alerts` + `production_get_status` → 生成待办清单（可选写备注）。
5. **盘点辅助**：识别盘点表 → `stocktake` 草稿 → 人审核 → 提交调整。

### 6.9 可观测性与回放

- 每个 Agent 请求：`request_id`、token、工具名、耗时、结果、创建/修改的实体 id；
- 可回放：根据 `agent_action_log` + `operation_log` 复现"某天 AI 做了什么"；
- 评测：维护一组"Agent 黄金任务"（10–20 个），每次升级 MCP/工具后自动跑，检查成功率、错写率、幂等（重复调用不重复入库）。

### 6.10 未来扩展（先留接口，不实现）

- AI 主动监控：库存/排产异常自动提醒（事件 + Agent 订阅）；
- 自然语言报表：Agent 调 reports/query 工具；
- 预测补货/最优排产：Agent 调 `schedule_propose` 时选择算法；
- 多 Agent 协作（收货 Agent、排产 Agent、盘点 Agent）：token 隔离 + 任务队列。

## 7. 联网方案（保留接口，不默认开启）

### 7.1 三种形态

| 形态 | 访问范围 | 做法 | 适用 |
|---|---|---|---|
| 本机（默认） | 仅本机 | 绑定 127.0.0.1；API/MCP 也只本机 | 单人/单机起步 |
| 局域网 | 车间/办公室 | 绑定 0.0.0.0 + 防火墙放行 + 账号/权限；HTTP 或内网 HTTPS | 多终端（推荐先做这个） |
| 远程（可选） | 外出/家里 | Tailscale/ZeroTier 组网（不暴露公网、不备案）；或云服务器 + HTTPS + 强认证 | 老板看数、外勤 |

### 7.2 联网安全设计（从第一天就写进 API）

- Token 鉴权（人用会话 + Agent 用 API token），scopes 最小化；
- API 版本化 `/api/v1`，OpenAPI 文档；
- 幂等键、请求 ID、限流（每 token/每分钟）、批量上限；
- 审计（谁、何时、从哪、做了什么）；
- 局域网模式强制独立账号、强密码、登录失败锁定；
- 远程模式必须 TLS（Caddy/Nginx/云负载均衡）+ 只读/受限角色 + 备份；
- 不允许 Agent 直接连数据库；不允许任意 SQL；不允许访问宿主机文件系统（除附件 API）。
- Token 与凭证：见 §6.3 生命周期；仅存哈希、一次性显示、可轮换/吊销。
- 传输：跨不可信网络必须 TLS；局域网 HTTP 仅限受控网段，并明确验收条件。
- Web 安全：CSRF/CORS 白名单、上传文件类型/大小/哈希校验、登录失败锁定、日志脱敏（token/密码/敏感字段不落日志）。
- 远程管理：Tailscale 只解决网络暴露，不替代应用认证与权限；远程操作需额外审计与只读/审批限制。

### 7.3 何时开启（决策规则）

- 只有 1 台电脑 → 本机；
- 有多台电脑/平板 → 局域网；
- 需要在家看/审批 → Tailscale（成本 0，最推荐），不建议直接公网映射端口；
- 需要外部客户/供应商登录 → 另做门户与合规评估（本期不做）。

## 9. 开发路线（三阶段 · 85–155 人日）

> 原则：**一期只证明"账 = 实、库存 = 生产"；二期只证明"排产能改善人工计划"；三期只证明"Agent 在受控范围内能安全干活"。** 每期独立验收、可停可退；不按功能数量计完成。

### 一期：账务闭环（55–95 人日，14–24 周）

| 阶段 | 内容 | 人日 |
|---|---|---|
| M0 业务事实与规则盘点 | 业务事实矩阵（§4.8）逐行确认；55 条规则处置；单据样例（磅单/化验单/送货单/投料记录）；主数据清单；验收口径 | 8–15 |
| M1 平台底座 | Django 工程、数据模型 v1、登录/角色、审计、启动器、内置运行时、一键备份/恢复/升级、健康检查、REST 只读骨架 | 10–16 |
| M2 主数据 + 仓储 | 物料/别名/共沸/储位/罐型标定/供应商/客户/塔/班组/字典；收货→入库→移库→出库→盘点→预留→预警；批次/质量基础 | 18–28 |
| M3 生产批次 | 工单、投料、产出（主产品/副产物/残液/损耗）、收率、班组、停机；批次追溯；库存—生产联动 | 12–20 |
| M4 对账与试运行 | 库存账=流水、生产消耗/产出对账、报表/导出、权限/审计完善、用户培训与双轨试运行 | 8–14 |
| **小计** | | **55–95** |

**一期验收（硬门槛）**：
1. 任一物料/批次可追溯：来源→收货→检验→入库→领用→工单→产出→销售；
2. 库存余额 = 流水合计，抽查 20 个物料/储位无差异；
3. 生产批次投料/产出与库存流水一致，收率可解释；
4. 盘点差异走调整凭证，不直接改余额；
5. 一键安装/备份/恢复/升级在干净机通过；
6. 10 个核心业务场景 UAT 签字。

### 10.2 Agent 黄金任务（可自动化跑）

- 任务 1：给一张磅单图片的识别 JSON → 生成草稿 → 校验通过 → 提交 → 库存 +N 吨，审计有记录。
- 任务 2：同一请求重复 3 次 → 只入库 1 次。
- 任务 3：篡改净重（毛重-皮重≠净重）→ 校验失败、不入库。
- 任务 4：无 commit 权限的 token 调 commit → 403。
- 任务 5：生成排产建议 → 修改一个 slot → 校验冲突 → 对比 KPI。
- 任务 6：识别结果物料不存在 → 进入待审核并提示建别名/主数据。

### 10.3 排产验证

- 约束覆盖测试：构造违反每一条约束（C1–C9）的订单，确认被拦截/告警；
- 确定性：同输入同参数两次运行结果一致；
- 可执行性：计划输出的每个 slot 时间不重叠、在日历内、罐容不超；
- KPI 合理性：准时率/利用率/切换次数与手工计算一致；
- 人工调整：拖拽后重新校验，冲突提示正确。

### 10.4 非功能与一键验收

- 一键 10 项（v2.0 §1.2）：干净机、二次启动、备份恢复、升级回滚、断电、端口、局域网、断网、杀毒。

### 14.3 给交叉评审 AI 的审查清单（重点攻击 21 点）

1. 产品定位：仓储+生产+排产定制 ERP，范围是否过大？MVP 切法是否合理？
2. 现有 Excel 作为"参考"是否被正确使用？有没有该继承却丢掉的规则/数据？
3. 排产模型：连续/间歇、单塔/多塔、切换清理、罐容约束、交期 vs 毛利，建模是否成立？还缺什么约束？
4. 排产 v1 规则+贪心是否够用？CP-SAT 放 v2 是否合理？如何验证"好计划"？
5. 仓储模型：余额+流水+预留+盘点+批次/质量，是否过度/不足？
6. Agent 集成：REST + MCP 双接口是否重复？是否应只做 MCP 或只做 API？
7. 写操作安全协议（草稿→确认→提交、幂等、限额、审计）是否有漏洞？自主级别 L0–L3 是否合理？
8. 图片/单据接入：由外部 Agent 识别、系统只做校验/入库，这个边界是否对？还需要哪些校验/存证？
9. 权限模型：人/Agent 同表但不同 token/scopes，是否能满足审计与最小权限？
10. 技术栈：Django + SQLite + HTMX + FastMCP 是否匹配"一键桌面 + Agent"？SQLite 在排产/并发下是否够？
11. 一键交付：便携运行时 vs 安装包 vs 单文件 exe，对非程序员哪个最优？
12. 数据模型：40+ 张表是否合理？实体/关系/状态机有没有明显缺失或冗余？
13. 联网：默认本机 + 局域网开关 + Tailscale，是否满足未来？API 安全设计是否够？
14. 工期：一期 55–95、二期 +15–30、三期 +15–30（合计 85–155 人日），是否低估（尤其排产与 Agent 联调）？
15. 测试：黄金用例/Agent 黄金任务/排产验证是否足够？还缺什么（并发、恢复、误操作、审计）？
16. 运维：备份/恢复/升级/杀毒/断电/token 轮换，还有哪些"一人维护"风险？
17. 合规：数据留存、附件（图片含单据信息）、Agent 操作审计，是否有遗漏？
18. 未来兼容：如果以后要云部署/多厂/多租户，现在的设计哪里会挡路？

### 14.4 已知局限

1. 排产是**计划工具**，v1 不承诺最优解；需要用户提供真实订单样例来验证"好计划"。
2. 图片识别质量取决于外部 Agent/插件；本系统只做校验/审核/入库与存证。
3. 生产/质量/成本模块的部分口径（收率、单位、价格、退税）需用户确认后才能定表。
4. 工期基于"AI 辅助 + 用户每周 3–4 天参与"的假设；排产与 Agent 联调是最容易超支的部分。
5. 本方案由 AI 编制，业务规则与排产约束需用户与外部评审确认后实施。
