## 0. 一页摘要（先看这页）

### 0.1 要解决的问题

现在的系统是"一个 Excel 文件 + 7,332 行 VBA（12 个窗体、208 个过程）+ 3 个 Python 脚本"，数据存在 Excel 工作表里，多个终端通过腾讯云 COS 上传/下载 JSON 文件来"同步"。它已经能跑，但存在三类结构性问题：

1. **数据层不可靠**：本地先改表、再传云端，没有事务；同步游标无条件前进，失败文件永久丢失；多终端同时修改时后写覆盖先写，没有冲突处理。盘点出 50 个缺陷，其中 7 个 S 级（会造成数据丢失或核心功能不可用）。
2. **代码不可维护**：12 个窗体、5,563 行有效代码里，业务规则全靠"隐式约定"（55 条，如液位必须精确落在 0.01 m 网格上、市场参考价是"2500-3500"这种文本时按 2500 计算），没有测试、没有文档、改一处要通读全文。
3. **能力不完整**：用户真正想要的利润/退税、生产排程、工艺分析，在现有文件里**根本不存在**；现有文件只有库存/仓库/储罐/五金/工艺卡/生产记录/日志，以及 4 张基础数据表。

### 0.2 推荐路线（一句话）

**把"多终端 + COS 文件同步"改造成"厂内一台中心服务器 + 浏览器访问"的纯 Python 应用：Django 5 + SQLite(WAL) + 少量 HTMX 做实时计算，先等价重建现有 12 个界面入口（10 个业务 + 2 个同步）和 9 张表，再迁移数据、双跑上线；COS 只保留做备份，不再参与业务写入。离线需求用"局域网 + UPS + 本地备份"满足，不采用"每个终端本地库 + 双向同步"（后者复杂度约为前者的 1.5–2 倍，且正是当前系统所有数据问题的根源）。**

- 核心开发量估算：**36–58 人日**（AI 辅助、单人开发，P0–P5；含 20% 缓冲约 43–70），日历时间约 **8–12 周**（按每周 3–4 天投入，含 2 周双跑）；利润/排程/工艺分析为二期，另计 15–25 人日。
- 一次性硬件成本：**0–2,000 元**（用现有办公电脑则 0）；年费：**0–150 元**（备份可选 COS/OneDrive，无服务器租用费）。

**与前序《项目说明.txt》的关系**：保留它的三个正确方向——"纯 Python""SQLite 类关系库""低成本、一人可维护"；明确不采纳它的三处结论——① Streamlit 做主录入界面（改为 Django，理由见 §4.3）；② 继续用 COS 做多端同步（改为中心化单库，理由见 §4.2）；③ 按它的 10 张表 SQL 建库（实际是 9 张表，且缺 4 张关键基础数据表，理由见 §2.5 C-02）。

## 2. 现状体检（证据化）

### 2.1 系统长什么样

- **形态**：11 张工作表（1 张可见的"操作界面"+ 10 张隐藏数据表）、12 个 VBA 窗体、40 个 VBA 组件、7,332 行代码（有效代码 5,563 行）、208 个过程、9 个 Excel 表格对象（ListObject）。
- **界面**：1 张企业厂区照片做背景，上面 12 个圆角矩形按钮，分别打开：共沸数据库管理、配件库出入管理、物料出入记录查询、工艺卡记录管理、基础物料信息管理、工艺卡记录查询、生产记录管理、生产记录查询、仓库出入库管理、储罐出入管理、同步、断网再上传。
- **数据**：4 张基础表有数据（4/3/4/12 行）；5 张业务表在快照里**全部 0 行**（只有 1 行空表体）。真正有业务数据的是旧版库（8 行示例库存）和一份独立的《投料记录》Excel（2 条）。

### 2.2 数据是怎么流动的（当前架构）

```
用户在 VBA 窗体里操作
  ├─ ① 直接改当前 Excel 表格（立即生效，无事务）
  ├─ ② 手工拼一段 JSON 文本
  ├─ ③ 以 GBK 编码写临时文件
  ├─ ④ 隐藏调用 C:\Scripts\upload_to_cos.py 传到腾讯云 COS
  └─ ⑤ 失败则把 JSON 丢进 C:\待同步\，弹窗提示，等人工点"断网再上传"
别的终端点"同步"
  ├─ 列出 COS 上"模块/年/月/日/"下的文件
  ├─ 按修改时间过滤、排序、下载
  ├─ 按模块用不同业务键去重/覆盖导入（库存=储位+名称+日期编号；工艺卡/生产=塔号+时间戳；五金/日志=时间戳）
  └─ 最后把"上次同步时间"改成当前时间（无论中间是否失败）
```

这套机制的**结构性缺陷**（不是某个 bug，而是设计问题）：

1. **双写无事务**：本地已经改了，云端才上传；上传失败不回滚，本地与云端必然分叉（D-08）。
2. **同步语义是"绝对状态覆盖"**：库存事件发的是"这条记录现在是多少"，不是"增减了多少"；两个终端先后导入，后到者静默覆盖先到者，没有版本号、没有冲突提示（D-09）。
3. **失败即永久丢失**：同步游标在循环结束后无条件推进到当前时间，失败的文件下次不会再拉（D-03）；而"断网再上传"的重试路径还原算法是错的，实际必然传错位置（D-04）。
4. **唯一键靠秒级时间戳/业务三元组**：同一秒两次操作会生成同名云端文件（互相覆盖），同秒两条日志会被当成重复丢弃（D-10/D-19）。
5. **基础数据不同步**：物料性质、共沸、储位、液位表这 4 张表不在同步列表里，各终端各有一份；密度/价格在录入端算好写进 JSON，另一端只存数值（D-13）。

### 2.3 为什么不能"把 VBA 逐行翻译成 Python"

盘点出的 55 条隐式业务规则和 50 个缺陷说明：现有 VBA 的"实际行为"与"表面意图"有大量偏差。举 6 个必须处理的例子：

| # | 现有行为 | 问题 | 迁移处置 |
|---|---|---|---|
| 1 | 市场参考价是 `2500-3500` 这样的区间文本，VBA 的 `Val()` 只取前导数字 → 总价一律按**下限**算 | 业务上是否正确未知；财务口径可能失真 | 保留"下限"为默认取价，但字段拆成"区间文本 + 生效价"，并在界面显示"按区间下限计算"【需用户确认】 |
| 2 | 储罐液位必须精确等于标定表里的 0.01 m 网格值（容差 0.0001），否则整笔拒绝 | 现场按液位计读数很难刚好是整数厘米；且 4 种罐型标定表在高液位段是空的/归零（D-14） | 默认保留精确匹配；新增"线性插值"选项（默认关闭），并把 4 种罐型的标定表补全作为上线前置条件 |
| 3 | 名称按"中文名"精确匹配取密度/价格，查不到返回 0，重量/总价静默变 0 | 库存里有 3 个示例名称（如"示例混料3"）不在物料主表里 → 全部算成 0 | 建立"库存名称→物料"别名表；未匹配时**阻断保存并提示**，不再静默写 0 |
| 4 | 共沸预警只看名称二元组，4 条"无稳定共沸"（甲醇-水、丙酮-水等）也会报警；14 个共沸组分名不在物料表 | 该报的不报、不该报的乱报，安全预警会被工人忽略（D-15） | 共沸表加"是否有稳定共沸"标志，重名/别名归一化；预警改为结构化判断并保留原文提醒 |
| 5 | 操作日志当前表缺"模块/变动液位/原液位/新液位"4 列（旧版有 13 列、现版只有 10 列），代码还在写这些列，错误被 `On Error Resume Next` 吞掉 | 日志字段静默丢失，无法审计"哪个罐、液位变多少"（D-05/D-18） | 新库日志表字段完整（含模块、液位前后值、操作人、终端），且所有业务模块统一写日志 |
| 6 | 仓库"新增入库"上传的 JSON 里数量/体积/重量/总价是 0（因为代码从没回填的文本框取值） | 别的终端同步过去看到 0 库存（D-02，S 级） | 新系统只在数据库事务提交成功后生成事件/审计，不再从界面控件取数 |

**结论：迁移的实质是"用测试把 55 条规则重新钉死，然后重写"，而不是翻译代码。** 这也决定了路线：先建规则测试与黄金用例，再写业务代码（见 §6 P0/P1）。

### 2.4 50 个缺陷里，迁移必须处理的（按影响排序）

| 编号 | 缺陷 | 级别 | 迁移处置 |
|---|---|---|---|
| D-01 | 仓库"出库清零删除"用 `deletedRecord` 键，导入端只认 `data` → 删除事件永远导入失败 | S | 新系统删除即数据库事务；审计表记录；不存在"事件导入" |
| D-02 | 仓库"新增入库"事件的数量/体积/重量/总价全为 0 | S | 从数据库已提交记录生成审计，不从 UI 控件取数 |

## 3. 目标原则：这次迁移到底在追求什么

1. **单一事实源**：一个数据库、一个写入入口，不存在"本地一份、云端一份"。
2. **算得准**：55 条业务规则有测试；关键数字（体积/重量/总价/库存合计）与旧系统对账到 0.01。
3. **改得动**：一人 + AI 能维护；代码分层（业务规则=纯函数、数据访问、界面分离），有测试和文档。
4. **丢不了**：事务、审计、每日备份、可恢复演练；任何写操作可追溯"谁、何时、改了什么"。
5. **用得惯**：保留用户熟悉的"表单 + 表格 + 导出 Excel"；不强迫用户学命令行。
6. **不镀金**：不上微服务、不上容器、不上前后端分离、不引入付费中间件——预算与维护人力都不允许。

## 4. 推荐架构（方案 A：厂内中心化 Web）

### 4.1 总体形态

```
      厂内局域网（交换机/WiFi）                         Internet（可选）
  ┌─────────────┐   ┌─────────────┐              ┌──────────────┐
  │ 办公电脑/平板 │   │ 车间平板/手机 │              │ 家里/外网设备  │
  │  浏览器      │   │  浏览器      │              │  浏览器        │
  └──────┬──────┘   └──────┬──────┘              └──────┬───────┘
         │                 │                            │ Tailscale/ZeroTier（可选）
         └─────────────────┴──────────┬─────────────────┘
                                      │ HTTP (局域网)
                           ┌──────────▼──────────┐
                           │ 厂内小主机（常开）     │
                           │ Django 应用 + SQLite │  ←── 每日备份 ──→ OneDrive/COS（可选）
                           │ 静态文件 + 会话/权限  │
                           └─────────────────────┘
```

- 客户端**不需要安装任何东西**，浏览器打开 `http://服务器IP:8000` 即可；手机/平板也能用。
- 服务器就是厂内一台常开的电脑（现有办公机即可，建议 4 核 8G、SSD、UPS）。
- 外网访问（如果确实需要）用 Tailscale/ZeroTier 组网：免费、不暴露端口、不需要公网 IP、不需要 ICP 备案；不需要时完全关闭。
- COS 从"业务同步总线"降级为"异地备份的一个副本"，不再参与任何写入路径。

### 4.2 为什么是"中心化"，而不是继续"本地 + 云同步"

这是全案最关键的取舍，必须讲清楚：

| 维度 | 现在的做法（本地 Excel + COS 事件） | 推荐做法（中心服务器） |
|---|---|---|
| 一致性 | 最终一致，且没有冲突规则；后写覆盖 | 强一致：一个库、一个事务 |
| 离线能力 | 断外网仍可录入（但同步常失败、失败会丢） | 断外网不影响；断**局域网**不可写入 |
| 代码复杂度 | 1,300 行 VBA 同步 + 3 个 Python 脚本 + 手写 JSON 解析器；仍需处理重试/游标/时区/冲突 | 同步层整体消失（约减少 1,300 行代码和 4 个 S 级缺陷） |
| 数据安全 | 每个终端一份 Excel，谁都能改；日志可编辑 | 服务器统一权限/审计/备份；终端只是浏览器 |
| 运维 | 每台机器都要装 Excel、Python、C:/Scripts、维护同步 | 只维护一台服务器；客户端零安装 |
| 成本 | COS 费用 + 多台电脑 | 一台常开电脑 + 备份空间（几乎为 0） |

用户担心的"工厂网络不稳定"，实际指的是**外网**不稳定——当前的 COS 同步恰恰依赖外网，所以经常失败。中心化方案只依赖厂内局域网（交换机/路由器），与外网无关，稳定性反而更高。**需要用户确认 Q2：断的是外网还是整个局域网；断网期间是否必须能写入。** 如果是后者，才考虑 §5.1 的方案 B（成本约 +50%~100%，且要重新设计同步，不推荐首选）。

### 4.3 技术栈（固定版本，避免"版本漂移"）

| 层 | 选型 | 说明 |
|---|---|---|
| 语言/运行时 | **Python 3.13（64 位）** | Django 5.2 LTS 官方支持 3.10–3.13；3.14 太新、部分轮子有风险；用 venv 隔离、锁版本 + 离线 wheelhouse |
| Web 框架 | **Django 5.2 LTS** | 自带账号/权限/后台管理/ORM/数据库迁移/表单校验/CSRF/国际化；文档与 AI 语料最厚，最适合"一人 + AI 维护" |
| 数据库 | **SQLite 3（WAL 模式）** | 单文件、零运维、备份简单；本系统写入量约每天几十~几百次，3–5 个用户完全够用；未来要换 PostgreSQL 时 ORM 基本不用改。**硬规矩**：库文件只放服务器本机 SSD（绝不放共享盘/OneDrive 同步目录/U 盘）；单写进程；`WAL + synchronous=FULL + foreign_keys=ON + busy_timeout=20000`；**金额存整数分**、体积/重量按 0.001 精度、时间存 UTC ISO8601；备份只用 `sqlite3.Connection.backup()`（不在运行中直接复制 .db 文件） |
| 前端 | Django 模板 + **HTMX + Alpine.js + Bootstrap 5** | 不引入 Node/前端构建链；HTMX 做"选物料→自动带出密度/价格/体积"等局部刷新；Bootstrap 保证表单/表格/响应式 |
| 图表 | ECharts（CDN 本地化）或 Chart.js | 生产/库存趋势、后续利润分析 |
| Excel 导入导出 | openpyxl（+ pandas 可选） | 导出保持用户熟悉的格式；导入模板校验 |
| 测试 | pytest + pytest-django + hypothesis | 规则测试、属性测试（液位→体积单调性等） |
| 部署 | **waitress + WhiteNoise + NSSM**（Windows 服务，自启/崩溃重启）；Linux 则 gunicorn + Nginx | 单进程 + SQLite；不启多 worker（避免多写者）；防火墙只放行局域网 |
| 备份 | sqlite3 `.backup` / `VACUUM INTO` + 7-Zip + 复制到 OneDrive | 每日自动、保留 30 天 + 12 个月度；每季度恢复演练 |
| 监控 | 应用内健康检查页 + 日志轮转 + 每日备份结果推送 | 不引入 Prometheus 等重组件 |

**为什么不用 Streamlit 做主界面**（TXT 的原始选择，这里明确推翻，理由可被反驳）：
1. 本系统是**事务型数据录入**（10+ 字段表单、选完储位自动带出区域/罐型、选完物料自动算体积/重量/总价、列表选中后做修改/出库/删除、二次确认、错误回填），不是数据看板。Streamlit 的"每次交互重跑整个脚本"模型会让这类交互用 `session_state` + callback 拼得很绕，状态 bug 比 Django 表单多。
2. 权限/登录/审计/数据库迁移/后台管理它都没有，需要第三方拼装，长期维护风险高。
3. 表格行操作、打印、Excel 导出、URL 路由都弱；用户要的是"替代 Excel 表单"，不是"一个数据展示页"。
4. **结论**：Streamlit 只适合做二期只读分析页或一次性原型；本方案用它做分析的"可选外挂"，不做主录入界面。
5. 反方意见（供评审）：如果用户明确只想要"看数+简单录入"，且不想维护服务器，Streamlit + 单机 SQLite 是最快路径；但那就等于放弃权限/审计/多端一致性，与 RQ-N7/P0 冲突。

**为什么不用 FastAPI + NiceGUI**（备选，不是主推）：NiceGUI 的实时联动体验更接近 Excel，纯 Python 也轻；但账号/权限/审计/后台/迁移都要自建，长期维护面更大。若做 3–5 天技术验证后认为 Django 表单交互太笨重，可切换到 NiceGUI（领域层与数据库层不变，只换 UI 层，切换成本约 5–8 人日）。**架构上把"业务规则/数据访问/界面"分层，就是为了保留这个可逆性。**

### 4.7 并发、事务、审计、权限

- **事务**：每个业务动作一个数据库事务（库存状态 + 流水 + 审计同事务提交）；失败整体回滚。
- **并发**：`version` 乐观锁——两个人同时改同一行时，后提交者收到"数据已被他人修改，请刷新"；不静默覆盖。
- **审计**：`operation_log` 只追加，不允许 UPDATE/DELETE（数据库触发器/权限双保险）；记录操作人、IP、前后值 JSON、request_id（幂等）。
- **权限**：管理员（全部 + 用户管理 + 参数）、录入员（业务录入 + 查询）、只读（查询 + 导出）。敏感操作（删除、改基础数据、改价格策略）仅管理员。
- **软删除/冲正**：业务数据默认不物理删除；删除=状态置为 void + 审计；确需物理删除的仅管理员并留审计。

### 4.8 多终端与"离线"的真实语义

- **多终端**：浏览器即终端，天然共享同一库；无需同步、无需安装、无冲突。
- **断外网**：不影响（不访问互联网；字体/JS 全部本地化，不引 CDN）。
- **断局域网/服务器故障**：系统不可写入。这是本方案**唯一接受的妥协**。缓解措施：
  1. 服务器接 UPS；用 SSD；开机自启 + 进程守护（挂了自动拉起）。
  2. 每日备份 + 每季度恢复演练；备份文件可离线打开（SQLite 文件）。
  3. 降级预案：服务器不可用时，用"空白 Excel 模板"手工记录，恢复后由录入员补录（模板与导入功能在 P2 就做好）。
  4. 关键岗位可保留一台"只读客户端"？——不必要，浏览器断网也打不开；不如备一台同配置小主机做冷备（可选，约 1,500–2,000 元）。
- **把"离线"拆成三层再讨论**（这个概念不清是方案反复摇摆的根源）：
  - **L1 外网中断**：能查询/录入 → 本方案天然满足（系统不依赖互联网）。
  - **L2 局域网/服务器中断**：能查询/录入 → 本方案不满足，接受"≤4 小时降级"（纸质/Excel 模板 + 恢复后补录，审计留痕）。
  - **L3 断电**：UPS 撑住服务器与交换机 ≥30 分钟；数据不丢（事务+备份）。
- **如果用户确认 L2 也必须能写入**：转方案 B（§5.1），成本 +40%~80%、风险上升，且必须重新设计离线队列与冲突规则。这是本次迁移最贵的一句话，必须在 P0 前回答。

### 4.9 部署与运维（一人可维护的具体做法）

1. **服务器**：Windows 10/11 或 Ubuntu 22.04 小主机；固定内网 IP；关闭自动睡眠；UPS。
2. **安装**：一个 `install.ps1`（或 `install.sh`）脚本：装 Python → 建 venv → 装依赖（离线 wheel 包同目录）→ 建库 → 建管理员 → 注册服务。
3. **启动**：NSSM 注册为 Windows 服务（或 systemd），开机自启；崩了自动重启；日志按天轮转。
4. **备份**：每天 02:00 备份数据库（`VACUUM INTO` 到 `backup/YYYYMMDD.db`）+ 打包 + 复制 OneDrive/COS；保留 30 天 + 12 个月度；备份完成后在首页显示"最后备份时间"。
5. **升级**：`upgrade.ps1`：先备份 → 拉代码/覆盖 → 跑迁移 → 健康检查 → 失败自动回滚到上一版备份。
6. **健康检查**：`/healthz` 返回数据库可写、磁盘剩余、备份时间；异常时页面顶部红条提示。
7. **文档三件套**：操作手册（md）+ 大白话版（txt）+ 架构说明；另加一页"故障排查速查"。

### 4.10 安全与合规

- **密钥**：COS 密钥从代码移出，放环境变量/Windows 凭据管理器；建议**轮换**当前明文密钥（C:/Scripts 三个脚本里是明文，任何拿到文件的人都能读写云桶）。
- **账号**：每人独立账号，禁用共享账号；离职立即禁用；密码策略由 Django 提供。
- **传输**：纯局域网可用 HTTP；若经 Tailscale，链路本身加密；如需浏览器 HTTPS，可在服务器装 Caddy 自动证书（可选）。
- **数据**：备份加密（至少 zip 密码 + 云端桶私有读）；导出文件含敏感价格/客户信息时限制权限。
- **合规**：本系统是内部经营数据，不替代法定危废台账/退税申报资料；是否需要在系统内生成合规台账，见 Q12（默认不纳入本期，保留导出扩展点）。

## 5. 备选架构与决策记录（ADR）

### 5.1 方案 B：本地优先 + 同步（仅在"断网必须写入"成立时）

- 形态：每台终端跑一个本地应用（Django/NiceGUI/桌面封装）+ 本地 SQLite；后台同步服务在终端之间/与中心服务器交换事件。
- 优点：断网可写入；保留现有"离线"体验。
- 缺点：必须重新设计同步（UUID、版本号、冲突策略、失败队列、幂等、时钟），工作量约 +40%~+80%；测试矩阵成倍增加；维护难度回到当前系统的老路。**这是本方案明确不推荐的首选，但在 Q2 答案为"必须离线写入"时是唯一可行方向。**
- 若必须做，建议"中心服务器 + 终端只读缓存 + 离线录入暂存队列（replay）"，而不是"每台终端一个完整库"；离线期间只允许新增/追加类操作，不允许修改/删除（降低冲突面）。

### 5.2 方案 C：云服务器 Web（公网）

- 优点：任何地方能访问，不用厂内常开机器；年费约 38–99 元。
- 缺点：依赖外网（工厂网不稳时最不可用）；需备案/域名/安全加固；数据在公有云；延迟更高。**不推荐做主方案；可作为"老板/外勤只读查看"的附加出口（同一数据库只读副本/API），且必须加认证与 HTTPS。**

### 5.3 方案 D：保留 Excel 前端 + Python 后端（过渡形态）

- 优点：用户界面不变，风险最小；可先解决数据层。
- 缺点：Excel 仍需 VBA/ODBC/宏安全设置；每终端安装与版本分发；双写/双轨长期化；无法真正"纯 Python"。**只建议作为 P5 双跑期的临时形态，不作为目标架构。**

### 5.4 决策矩阵

评分：5=最好，1=最差（针对本项目的权重：一致性/可维护/离线/成本/可逆性）。

| 维度 | A 中心化 Web | B 本地+同步 | C 云 Web | D Excel 前端+Python 后端 |
|---|---|---|---|---|
| 多端一致性 | 5 | 2 | 5 | 2 |
| 断网可用（写入） | 1（仅局域网） | 5 | 1 | 5 |
| 一人可维护 | 5 | 1 | 4 | 2 |
| 开发工作量（越少越好） | 4 | 1 | 4 | 3 |
| 成本 | 5 | 3 | 4 | 3 |
| 可逆/演进 | 5 | 3 | 4 | 1 |
| **结论** | **主推** | **条件备选（Q2=必须离线写入时）** | **附加只读出口** | **仅过渡** |

**加权评分（独立架构评审给出，权重：离线 20/一致性 20/运维 15/开发 10/维护 15/安全 10/成本 5/可逆 5）**：A 中心化 **4.10**；B 本地+同步 **2.45**；C 云 Web **3.20**；D Excel+Python 后端 **2.90**。

**触发切换条件（若任一条为真，主方案 A 被推翻）**：
1. Q2 要求"断局域网/服务器宕机也能写入" → 只能方案 B（工期 ×1.5~1.8，需重新设计离线队列与冲突规则）。
2. 厂内无法提供常开且可接 UPS 的机器，且不允许购买 → 方案 D 过渡或继续用 Excel（不推荐）。
3. 实际并发写 >10 人或跨 3 个以上厂区 → 评估 PostgreSQL / 方案 C。
4. 用户拒绝浏览器且不接受培训 → 方案 D 过渡。
5. 合规要求数据不能落厂内单机 → 方案 C（加认证/HTTPS）。

**对账流程（P0 完成）**：

### 7.3 清洗规则（必须在导入前定版）

1. **名称归一**：去首尾空格/全半角统一；5 个带尾随空格的物料名；34 个库存名称进别名表（无把握的标"待用户确认"，不自动猜）。
2. **价格**：区间文本拆低/高值；"~610" 这类非价格文本→NULL + 告警；缺失价格不阻断主数据导入，但阻断"算总价"的业务录入（提示补价）。
3. **液位表**：4 种罐型缺失段（25 方/60 方 2.91 m 起归零；40 方 2.51 m 起空白；50 方 2.91 m 起空白）→ 由用户/工程提供补全值；补全前这些罐型的对应高液位业务在系统内**拒绝并提示**（不静默算 0）。
4. **方量口径**：旧版"示例库区1#/100"与当前"示例库区2#/5"冲突 → 以用户现场为准，形成《储位与方量确认表》。
5. **重复行**：旧库存 8 行中有 2 组重复业务键（同一储位+名称+空日期编号多行）→ 按业务键合并或保留为多批次（需用户确认）；合并规则写入迁移报告。
6. **时间/时区**：旧 JSON/日志时间按 Asia/Shanghai 解释；2006 年等异常日期标记并人工确认；统一存 UTC，显示本地时间。
7. **编码**：旧 JSON 是 GBK、CSV 是 UTF-8-SIG；导入器做编码探测并记录；新系统统一 UTF-8。

### 7.4 迁移程序要求（工程约束）

- **可重复运行**：每次导入生成 `import_batch`（来源文件哈希、行数、错误数）；重复运行不产生重复数据（按业务键 upsert）。
- **dry-run**：先输出"将新增/更新/跳过/报错"统计与样例，用户确认后才写库。
- **不覆盖人工修改**：迁移只写 `imported` 标记的数据；人工修订后再次导入时跳过并报告。
- **错误隔离**：单行错误不阻塞整批，错误行导出 CSV 供人工修。
- **只读源文件**：迁移脚本只读旧文件（复制副本），绝不修改原 xlsm/xlsx。

### 7.5 对账指标与切换/回滚

**对账指标（切换前 + 双跑期每日）**：
- 主数据：4 张表条数、关键字段值逐条相等（价格/密度/沸点等数值容差 0.001）。
- 库存：按储位/区域/物料的体积合计、重量合计、金额合计（容差 0.01 元）；行数；空值行数。
- 五金：按名称+型号的结存数量、金额合计。
- 生产：工艺卡/生产记录/投料记录条数、按塔号/月份汇总的数量与收率。
- 日志：双跑期新系统日志条数 = 业务动作数；关键动作 100% 有记录。
- 差异必须逐条解释（可接受差异：旧系统空值/单位不明/用户确认修正），不允许"总数对得上就过"。

**切换日步骤**（半天，建议周五下午/周末）：
1. 冻结旧系统：取消共享、通知停止录入、旧文件另存只读副本 + 哈希。
2. 导出最终快照（旧版 + 当前版 + 投料记录），跑最终迁移（dry-run → 正式）。
3. 跑全量对账脚本，生成报告；差异为 0 或有签字解释。
4. 打开新系统，用户按 SOP 做 5 个典型操作，确认无误。
5. 公告上线；旧系统只读保留 2 周。
6. 若出现严重问题：旧系统恢复写入（解除只读）+ 新系统期间数据导出 Excel，按手册回填；或整体回退到切换前数据库备份。

### 10.1 开发与协作规范（"纯 Python 怎么开发"）

> 用户不是职业程序员，真正的开发方式是"AI 写 + 人验收 + 每步可回滚"。以下规矩用来防止 AI 编码常见的失控。

| 项 | 规矩 |
|---|---|
| 版本控制 | 本地 git 仓库（代码 + 迁移脚本 + 文档）；每天自动 `git bundle` 备份到备份目录；不上传包含密钥/生产数据的文件 |
| 分支与提交 | `main` 始终可运行；每个功能一个分支；提交小步（一次 < 200 行/单一目的）；提交信息中文写"做了什么、为什么" |
| 测试门槛 | 业务规则（domain/）先写测试再写实现；每次提交跑 `pytest`；每阶段跑 20 条黄金用例 + 对账脚本 |
| 代码评审 | AI 生成的代码由"另一个 AI 会话"按 §12.3 清单评审；涉及计算规则/数据模型的改动必须人工确认；不直接把 AI 输出贴进生产 |
| 部署门槛 | 只允许通过 `upgrade` 脚本发布：自动备份 → 迁移 → 健康检查 → 失败自动回滚；不许手工改生产库 |
| 文档 | 每个 app 一个 README；对外三件套（操作手册 md / 大白话 txt / 架构说明）；维护 CHANGELOG |
| 配置与密钥 | 密钥只放环境变量/凭据管理器；生产数据不进 git；`settings.py` 不写死路径 |
| 变更管理 | 新需求先记录 → 评估人日与影响 → 排进下个迭代；不在里程碑中途改范围 |
| 验收 | 每个里程碑：演示 30 分钟 + 四件套（变更说明/对账/测试输出/未验证项）+ 用户签字 |

### 12.3 给交叉评审 AI 的审查清单（请重点攻击这 15 点）

1. **架构判断**：中心化局域网 Web 是否适合"工厂网络不稳 + 多终端 + 一人维护"？是否低估了"断网写入"的真实需求？

3. **Django vs FastAPI+NiceGUI vs Streamlit**：对"AI 辅助、一人维护、表单密集"的判断是否成立？有没有更合适的（如 Django Admin 为主 + 少量自定义页）？
4. **SQLite 是否够**：3–5 用户、每天几十~几百写、5 年数据，WAL + 单进程是否有隐患？何时必须 PostgreSQL？

10. **迁移源判断**：旧版 8 行 + 示例投料 2 条 + 当前版主数据，是否漏了什么（其他终端、COS 历史、微信/邮件里的表）？
