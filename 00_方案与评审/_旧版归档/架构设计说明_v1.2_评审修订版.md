> 6. 删除价格区间/价格策略代码与字段：金额以单据明细为准（I-05）。
> 7. 库存粒度、密度/标定快照、附件完整性、配方快照、甘特冲突分级、确认凭证均补明确（I-02/I-03/I-06/I-07/I-08/I-09）。
> 8. Vibe Coding 改为风险分级流程（I-10）；不只写"每次写后全库扫描"，改为事务内局部校验+手动全库对账。
> 9. **用户声明：图像识别插件已完成**。一期范围调整为：仓储 + 报表 + 识别结果接入（接口/草稿/审核/人工确认）；生产模拟、甘特后置（§10）。

## 0. 用户决定与架构含义

| # | 用户决定 | 对架构的直接影响 |
|---|---|---|
| 1 | 暂时单机，预留升级联网 | 应用始终按"服务端 + 浏览器"写，单机只绑定 127.0.0.1；联网时改绑定地址 + 账号/权限 + 防火墙，不改业务代码；数据库从 SQLite 起，预留 PostgreSQL 切换点 |
| 2 | 生产模式以间歇批次为主 | 生产模拟按"批次"建模：一批投入 → 周期 → 产出/产废；甘特排产按批次日/班次排，不做连续流程的复杂建模 |
| 3 | 库存计量以重量为主（体积×密度得出） | 库存主账为重量（吨），流水与余额都以重量为不变量；体积/液位作为来源测量与容量校验；密度、标定版本、称重来源必须留快照 |
| 4 | 生产模块只做"投入原料后的预计周期、产品产量预估、产废预估" | 不做完整工单/开工/完工/质量放行/实际消耗；生产模拟是"测算器 + 历史对照"，不自动改库存 |
| 5 | Agent 正式过账全部人工确认 | Agent 只能查询、生成草稿；所有落业务表的操作必须人在界面确认；不设 L2 自动过账 |
| 6 | 排产价值主要是甘特图 | 排产 = 订单池 + 塔/日视图 + 人工拖动 + 冲突提示 + 版本；不做贪心/CP-SAT 优化器 |
| 7 | 业余时间开发 | 里程碑按周粒度、每个会话可完成一个小任务；文档/测试/AI 协作规范必须降低上下文切换成本 |
| 8 | 记录保留期限由企业负责人决定 | 系统提供按类别的保留策略配置，只执行批准策略；不写死年限 |
| 9 | Windows 原生直接运行 | 便携 Windows 运行时 + 浏览器；不引入 WSL/Linux/虚拟机/Docker；安装/启动脚本用 PowerShell/批处理 |
| 10 | 一律按净重结算、单据自带明细 | 重量主账与金额都以单据净重/明细为准；系统只校验，不做价格口径推断 |
| 11 | 不需要备份 | 不实现备份/恢复；只保留导出（Excel）与操作审计；风险由用户接受 |
| 12 | 图像识别插件已完成 | 本应用不开发 OCR；只提供识别结果接入 API/草稿/审核/人工确认；插件输出建议 JSON，不直接执行 SQL |
| 13 | 一期优先仓储+报表+Agent 链接 | 一期交付仓储闭环、报表、识别结果接入；生产模拟与甘特排产放到后续阶段 |

**一句话定位**：做一个**单机优先、重量记账、批次模拟、人工甘特、Agent 只读/草稿**的轻量定制应用；Excel 只作业务参考，不再参与运行。

## 1. 范围与不做

### 1.1 本期要做（MVP）

| 模块 | 内容 |
|---|---|
| 一期：主数据 | 物料（含别名/密度/安全信息）、储位/储罐/罐型标定、供应商/客户、单位、字典；塔/配方可先建最小表 |
| 一期：仓储 | 收货（磅单/单据）→ 入库（仓库/储罐）→ 移库 → 出库 → 盘点 → 预警；批次/质量基础；库存过账模型（§5.1.1） |
| 一期：报表 | 库存台账（重量）、收发存、库存预警、批次追溯、Excel 导出；独立对账脚本 |
| 一期：识别接入 | 图像识别插件结果接入：JSON/SQL 转换 → 校验 → 草稿 → 审核 → 人工确认 → 过账；不做 OCR |
| 一期：系统 | 用户/角色、审计、一键启动、升级、健康检查（**不做备份/恢复**） |
| 二期：生产模拟 | 投入→周期/产量/产废预估；公式/假设/版本/质量平衡（按 §5.3 修订后） |
| 二期：甘特排产 | 批次池 + 塔/日甘特 + 人工拖动/冲突/版本；先原型验证，不承诺完整模块 |
| 后续：通用 Agent | 只读查询/草稿/人工确认；MCP 后期薄适配 |

### 1.2 本期不做

- 完整工单执行（开工/暂停/完工/停机/质量放行）、实际生产记录、实际消耗/产出过账；
- 排产优化器（贪心/局部搜索/CP-SAT）——甘特只做人工；
- 多厂/多租户/云部署/移动 App/公网门户；
- 完整成本/税务/财务核算（金额按单据明细，不做价格推断）；
- 采购/五金扩展（预留模块边界，不在本期）；
- 把旧 Excel 业务数据迁入（用户确认是测试数据）；
- 生产模拟与甘特完整模块（二期；一期只保留数据字段/原型）。

### 1.3 成功标准

1. Windows 单机双击即用；断外网可用；启动/升级/健康检查通过；不依赖 WSL/Linux/虚拟机/Docker。
2. 重量账可追溯：任一物料/批次从收货到出库，重量余额=流水合计，抽查 20 组无差异；金额与单据净重/明细一致。
3. **二期目标（非一期验收）**：生产模拟输入 10 组真实原料/配方，输出周期/产量/产废在业务可接受区间；假设可解释。
4. **二期目标（非一期验收）**：甘特能把 20–50 个批次排进塔/日视图，人工调整后冲突提示正确，计划可发布/打印。
5. Agent：能读取数据、生成图片识别草稿；提交必须人工确认；重复提交不重复入库；全程审计。
6. 用户独立使用 ≥3 天无阻塞；文档三件套齐全。

## 2. 总体架构

### 2.1 单机形态

~~~text
Windows 电脑
┌──────────────────────────────────────────────────────────────┐
│  BR数据系统.exe（启动器，tkinter，无控制台）                    │
│   ├─ 检查环境/数据库/版本                                      │
│   ├─ 启动 waitress（Django 应用）127.0.0.1:8765                │
│   ├─ 可选启动 MCP 服务 127.0.0.1:8766（后期可选）               │
│   ├─ 打开默认浏览器                                            │
│   └─ 启动/停止/升级/日志/Agent 开关                             │
│                                                              │
│  Django 应用（单进程）                                          │
│   ├─ Web 界面（Django 模板 + HTMX + Alpine + Bootstrap）        │
│   ├─ REST API（Django Ninja，/api/v1）                         │
│   ├─ 领域层（纯 Python：重量换算、模拟、甘特冲突）               │
│   ├─ 服务层（事务、权限、审计）                                 │
│   └─ SQLite（WAL）+ 附件目录 + 日志                             │
└──────────────────────────────────────────────────────────────┘
~~~

- 单机不装 Python、不装 Office；便携目录 + 内置运行时。
- 浏览器只连本机；启动器负责生命周期。
- 数据目录可配置（默认程序目录下 data/）；**不做备份/恢复**。

### 2.2 升级联网版（预留，不现在做）

- 同一套 Django 应用绑定 0.0.0.0:8765；用户在系统内建账号/角色；Windows 防火墙放行；客户端浏览器访问。
- 认证：Django session + 登录；API/MCP 用 token；局域网 HTTP 仅限受控网段，跨网/远程加 TLS。
- 数据库：SQLite 仍可支撑 2–5 个低并发用户；触发条件（并发写明显增加/多进程/远程 BI/数据量）再换 PostgreSQL。
- **不提前加 org/site/warehouse 等多租户字段**；先把认证/URL/附件/配置边界留在服务层，等有真实多厂需求再加。
- 不改代码结构，只改配置与部署方式。

## 3. 后端架构说明

### 3.1 分层

~~~text
接口层 apps/api、apps/web        ← 参数校验、权限入口、渲染/JSON
应用层 apps/*/services.py        ← 用例编排、事务边界、审计
领域层 domain/                   ← 纯函数：重量换算、模拟公式、甘特冲突、校验
数据层 apps/*/models.py + migrations
基础设施 core/                   ← 启动、配置、日志、附件、健康检查
~~~

规则：
- domain 不 import Django；可用 pytest 单独测。
- 所有写操作走 services；视图/API 不直接写 ORM。
- 事务用 transaction.atomic；短事务；库存更新用 select_for_update 或版本检查（SQLite 下单写串行，但仍要校验版本）。
- 审计与业务写入同事务。

### 3.2 Django 应用划分

| App | 职责 |
|---|---|
| masterdata | 物料/别名/密度记录、储位/罐型/标定、塔/班组/供应商/客户/单位/字典、配方 |
| inventory | 收货、入库、移库、出库、盘点、预留、库存余额/流水、预警 |
| production_sim | 生产模拟：情景、输入、配方参数、结果、假设、历史对照 |
| scheduling | 订单/批次池、甘特计划、slot、冲突、版本/发布 |
| ingestion | 图像识别插件结果接入、映射、校验、草稿、审核、人工确认（一期） |
| auditlog | 通用审计与操作回放 |
| reports | 查询、汇总、Excel 导出 |
| accounts | 用户/角色/权限 |
| core | 启动器 API、健康检查、配置、版本 |

### 3.3 领域层核心模块

| 模块 | 内容 |
|---|---|
| domain/units.py | 重量/体积/密度/金额换算；Decimal 精度；单位归一 |
| domain/posting.py | 库存过账：业务单据→过账事件→有符号重量流水；一次过账一次增量；移库同事务 |
| domain/weight_stock.py | 重量主账规则：余额=期初+Σweight_delta；容量校验用体积；来源/换算快照 |
| domain/production_sim.py | 模拟公式：周期、产量、副产物、产废；假设与版本 |
| domain/gantt.py | 甘特约束校验：塔重叠、班次、罐容、最小批量；冲突对象 |
| domain/validation.py | 业务校验：必填、范围、状态机 |
| domain/azeotrope.py | 共沸预警（沿用但作为辅助） |

### 3.4 服务层（关键用例）

- InventoryService：receive、putaway、transfer、ship、stocktake、reserve/release。
- ProductionSimService：create_scenario、calculate、save_result、compare。
- SchedulingService：create_plan、move_slot、validate、publish、archive。
- IngestionService：create_draft、validate、approve、commit、reject。
- ReportService：stock_ledger、movement_report、sim_report、gantt_export。
- AuditService：log、query、replay。
- BackupService：backup、restore、verify。
- AgentService：token 校验、scope 校验、请求日志。

### 3.5 接口层（REST API）

- 路径前缀 /api/v1；OpenAPI 文档 /api/v1/docs。
- 认证：本机默认关闭或仅 token；联网后 Bearer token/会话。
- 统一错误：{code, message, details, request_id}。
- 幂等：写接口 Idempotency-Key。
- 只读接口先做：materials、locations、inventory、simulations、schedule。
- 草稿接口：ingestions、receipts/draft、simulations/draft、schedule/draft。
- 提交接口：所有 commit 需要人工确认 token（本期不提供 Agent 自动 commit）。
- MCP：后续可选，把只读+草稿包装成工具，调同一 API；不实现第二套逻辑。一期只做 REST。

### 3.6 数据一致性

- 库存重量余额 = Σ 重量流水；体积/液位为来源与容量校验，不参与重量余额相加。
- 金额 = 重量 × 单价快照；历史金额不因主数据价格变化而改。
- 幂等键唯一约束；单据号/批次号唯一；版本字段。
- 每日/每次写后校验；不一致告警并冻结相关操作。

### 3.7 后台任务

- 不做 Celery。导出、模拟计算用同步请求或管理命令；长任务用线程 + 进度页（可选）。
- 甘特/模拟计算量小，单机同步可接受。

## 4. 前端架构说明

### 4.1 页面地图

| 区域 | 页面 |
|---|---|
| 首页 | 仪表盘：库存重量概览、低库存/高液位、最近模拟、本周计划 |
| 主数据 | 物料列表/编辑、别名、储位、罐型标定、塔、班组、配方、供应商/客户、字典 |
| 仓储 | 收货单、入库、库存台账、移库、出库、盘点、预警 |
| 生产模拟 | 新建模拟、模拟结果、情景对比、历史对照 |
| 排产 | 订单/批次池、甘特图、计划版本、冲突列表、发布 |
| 报表 | 库存/收发存/模拟/计划报表、导出中心 |
| 系统 | 用户/角色、审计日志、Agent 连接、设置 |

### 4.2 交互模式

- 服务端渲染 + HTMX 局部刷新；表单 POST 提交、服务端校验、错误回显。
- 选物料/储位/罐型 → HTMX 局部更新密度/价格/体积/容量提示。
- 表格：分页、筛选、排序（服务端）、导出 Excel；操作按钮行内。
- 甘特：左侧塔列表 + 右侧时间轴；拖动/拉伸触发 POST，返回冲突后重绘。
- 所有删除/发布/提交需二次确认；危险操作显示影响摘要。
- 中文界面；术语与 Excel 一致；每页有简短操作说明。

### 4.3 前端技术约定

- 不使用 React/Vue/Node 构建；HTMX 负责请求，Alpine 负责局部状态（弹窗/折叠）。
- 静态资源全部本地化（Bootstrap/HTMX/Alpine/Frappe Gantt），断网可用。
- 表单用 Django Forms/ModelForm；前端只做提示，不做最终校验。
- 金额/重量显示格式统一：重量 0.001 t、金额 0.01 元、体积 0.001 m³；服务端格式化。
- 打印样式：A4 横向甘特/报表；不依赖浏览器插件。

### 4.4 前后端边界

| 关注点 | 前端 | 后端 |

## 5. 核心业务设计

### 5.1 重量主计量库存模型（本次决定的核心）

**主账 = 重量（吨）。** 所有库存余额、流水、报表、金额以重量为准；体积与液位是来源测量/容量校验，不单独累计。

| 数据 | 规则 |
|---|---|
| 收货 | 磅单净重（实测）为结算重量；同时记录体积/密度计算值；差异超阈值挂异常，按合同/业务口径选择 |
| 储罐入库 | 液位 → 体积（标定版本）→ 重量（密度快照）；重量入主账；体积用于罐容校验 |
| 仓库入库 | 按件/桶/吨：件数×单件重量 或 直接重量；体积为辅助 |
| 出库/销售 | 以重量为准；若客户按体积结算，按出库时密度快照换算并记录 |
| 移库 | 重量守恒；体积/液位按目标储位重新计算；混罐生成新批次与来源链 |
| 盘点 | 实盘重量（或体积×密度）与账面重量差异；调整凭证 |
| 金额 | 按单据明细（净重 × 单价）直接录入并校验合计；系统不推断价格口径 |
| 不变量 | 主账余额=Σ重量流水；体积/液位不单独累加；不同单位/物料/质量状态不混加 |
| 换算公式 | 体积(m³)=重量(t)/密度(g/mL)（1 g/mL = 1 t/m³）；罐容校验用体积≤最大方量；重量账不因体积换算而改写 |

字段要求：stock_item 存 account_weight_t、source_level_m、source_volume_m3、density_used、density_source、calibration_version、weight_source（weighbridge/calculated）、amount_cents；movement 存 **weight_delta_t**、weight_before/after、volume_before/after、level_before/after、density/calibration 快照、document_price/amount、variance。附件先落临时文件校验哈希，再建引用；缺失/哈希不符阻断相关操作。

#### 5.1.1 库存过账模型（P0-1/P0-2/P0-3 修订）

**三层必须分开，不能让页面直接改余额：**

| 层 | 内容 | 规则 |
|---|---|---|
| 业务单据 | receipt_order/line、shipment_order/line、transfer_order、stocktake | 只记录事实与明细，**不直接改库存**；未过账的收货单不增加库存 |
| 库存过账事件 | stock_posting | 一次实际入库/出库/移库/调整；带 posting_no、状态、来源单据行、过账时间、操作人；同一单据行只能成功过账一次 |
| 库存流水 | stock_movement | 不可变；有符号 weight_delta_t；余额=期初+Σ增量；before/after 只作审计，不参与求和 |

**规则：**
1. 收货建单 → 确认/检验 → **过账**才产生一次重量增加；过账失败或未过账不增加库存。
2. 移库 = 一出一入两条流水，**同事务**完成；仓库↔储罐同理。
3. 冲销 = 反向流水；下游已使用时走受控反转，不得直接删行。
4. 期初库存必须通过"期初建账凭证"审批后生成 open 流水；**禁止手工改余额**。
5. 余额更新、流水追加、审计记录、过账事件必须在同一事务；before/after 仅用于审计与校验。
6. **一次收货只允许一个过账重量来源**：默认磅单净重（结算/过账）；液位×标定×密度只作换算参考、罐容校验、差异分析；差异超阈值进入"待处理"，不得自动选大/小/平均值。
7. 若业务确实要求按罐测重量调整，必须单独定义审批流程与适用场景，系统不自动切换口径。

### 5.2 仓储流程（简化但完整）

收货 → 检验/放行（可选基础字段）→ 入库 → 移库 → 出库 → 盘点 → 预警。
- 预留：订单/模拟批次可预留重量，不生成流水；
- 批次：lot_no + 质量状态；质量不合格/冻结不可出库；
- 盘点：快照 → 实盘 → 差异 → 审批 → 调整流水；
- 红冲：不物理删除；下游已使用时走受控反转。

### 5.3 生产模拟（投入 → 周期/产量/产废预估）

**定位：测算与决策辅助，不做实际生产执行、不自动改库存。**

输入：
- 原料：物料/批次/重量（可多行）、成分（可选）；
- 配方：主产品、收率、副产物比例、产废比例、周期（小时/天）、塔兼容、最小/最大批量；
- 参数：塔、批次量、班次假设、损耗/含水率（可选）。

输出：
- 预计周期（小时/天）；
- 主产品产量（吨/收率%）；
- 副产物/残液/废水/废气（吨或占比）；
- 产废预估（吨/占比）；
- 关键假设与参数来源、置信度/历史对照。

**首版计算公式（可配置、可版本化，必须做质量平衡）**

- 主产品产量 = 投入重量 × 主产品收率（或按配方分段收率）
- 副产物/残液/废水/废气 = 投入重量 × 各自比例
- 产废量 = 投入重量 × 产废比例（或按质量平衡倒算）
- 损耗 = 投入重量 − 主产品 − 副产物 − 产废；必须 ≥0 且 ≤阈值
- 周期 = 配方基准周期 × 批量系数（或 setup + 批量 / 处理速率）
- 质量平衡校验：Σ产出/产废/损耗 = 投入；偏差超过阈值时提示"参数需校准"，不给出高置信度

功能：
- 情景保存/复制/对比；
- 参数版本化（配方/收率/周期）；
- 与历史实际（若有）对比，显示偏差；
- 结果可导出 Excel；
- 明确标注"预估"，不写入库存。

数据：simulation_scenario、simulation_input、simulation_result、simulation_assumption、recipe（yield/cycle/waste 参数）。

### 5.4 甘特排产（人工为主）

- 数据：订单/模拟批次池、塔、班次/日历、计划版本、slot、冲突。
- 视图：塔为行、日期/班次为列；拖拽移动/拉伸；锁定；发布。
- 冲突检测：塔时间重叠、班次外、罐容（用重量→体积）、最小批量、质量状态（若启用）。
- 不做自动优化；可提供"放入最近空档"的简单辅助（可选）。
- 版本：草稿/发布/归档；发布后只读，改动需新版本或审批。
- 导出：甘特 PNG/PDF/Excel（先做 Excel/打印，PNG/PDF 可选）。

### 5.5 Agent 与图像识别插件接入（全部人工确认）

**前提：DSH 桌面版的图像识别插件已经开发完成；本应用不再做 OCR/识别，只做"识别结果 → 业务数据"的受控接入。**

#### 5.5.1 插件输出契约（建议 JSON，不直接执行 SQL）

~~~json
{
  "document_type": "weighbridge_receipt",
  "source": {"filename": "IMG_001.jpg", "sha256": "...", "image_path": "..."},
  "extractor": {"name": "dsh-table-extract", "version": "1.2"},
  "confidence": 0.93,
  "data": {
    "supplier": "某药业", "plate_no": "苏K12345",
    "gross_kg": 32560, "tare_kg": 11840, "net_kg": 20720,
    "material_name": "甲醇废液", "date": "2026-10-27", "ticket_no": "BD20261027001"
  },
  "lines": [
    {"material_name": "甲醇废液", "net_kg": 20720, "location": "示例库区1#"}
  ]
}
~~~

**如果插件当前输出的是 SQL 语句：不要直接执行。** 两种安全做法：
1. 让插件/中间层把 SQL 结果转成上述 JSON（推荐）；
2. 如果只能给 SQL，应用侧只解析**白名单表的参数化 INSERT 值**，转成 JSON 再走同一校验；**禁止执行任意 SQL、DDL、UPDATE/DELETE**。

#### 5.5.2 接入流程

~~~
插件识别 → 调 POST /api/v1/ingestions（JSON）或落 data/inbox/*.json
→ 应用按 document_type 找 ingestion_profile（字段映射/单位/去重键）
→ 校验（必填/数值/净重=毛重-皮重/物料/储位/重复单据/重复图片/罐容）
→ 生成 ingestion(draft) + 行级问题
→ 人工审核页（左图右表、低置信度标红、字段来源定位）
→ 人工确认 → 过账（调用库存服务，生成 posting + movement + 审计）
→ 返回单据号/库存变化；原图按 SHA256 存证
~~~

#### 5.5.3 安全与边界

- Agent/插件只能：查询、校验、生成/修改草稿；**所有正式过账必须人工确认**，不提供自动 commit。
- token：独立身份、scope（只读/草稿/提交申请）、有效期、撤销；所有调用进审计。
- 幂等：文件哈希 + 业务键（单号/日期/供应商/金额）+ Idempotency-Key；疑似重复不自动过账，转人工关联。
- MCP 可选（后期薄适配），一期只做 REST；插件也可用文件落盘方式接入。

| 项 | 单机默认 | 升级联网时 |
|---|---|---|
| 绑定地址 | 127.0.0.1:8765 | 0.0.0.0:8765；防火墙放行 |

## 9. AI 辅助 Vibe Coding 开发规范（重点）

> 目标：让"业余时间 + AI 写代码"能持续产出可维护、可验证的代码，而不是一堆看起来能跑、改不动的页面。

### 9.1 十条铁律

1. **规格先行**：每个功能先写"输入/输出/验收标准/涉及表/异常"，再让 AI 写代码；没有验收标准不写。
2. **小步提交**：一次会话只做一个可验收的小功能（≤1–2 小时），提交一次 git；不跨模块大改。
3. **先测试后实现（按风险分级，见 §9.12）**：库存过账/权限/迁移必须测试先行；纯展示页面只需页面验收。
4. **文档即上下文**：仓库里维护 PROJECT/ARCHITECTURE/DECISIONS/TASKS/CHANGELOG 五份短文档；每次只更新受影响的那几份。
5. **不许猜**：AI 不确定的字段、接口、Django 用法，先查本项目文档/官方文档/问用户，不许编。
6. **一次只改一处**：要求 AI 输出"改哪些文件 + 为什么 + 测试命令"；不许顺手重构无关文件。
7. **可运行证据**：每个任务结束必须跑测试/启动页面，把结果贴回来；"应该可以"不算完成。
8. **数据安全**：不把真实生产数据/密钥贴给 AI；用合成样例；改数据库结构前确认迁移可回退。
9. **人做最终评审**：AI 生成的代码必须人工/另一 AI 会话按清单评审，重点看权限、事务、金额、时间、迁移。
10. **范围冻结**：新想法进 TASKS 的"以后再说"，不插队；每两周只处理一个里程碑。

### 9.2 仓库与文档结构

~~~text
br-app/
├─ app/                     # Django 代码
├─ docs/
│  ├─ PROJECT.md            # 一句话目标、用户、范围、不做
│  ├─ ARCHITECTURE.md       # 本文件精简版（分层/表/接口）
│  ├─ DECISIONS.md          # ADR：每个决策、理由、日期
│  ├─ TASKS.md              # 当前/下一个/以后；WIP 限制 1
│  ├─ CHANGELOG.md          # 每次提交做了什么
│  └─ TESTPLAN.md           # 黄金用例与验收清单
├─ tests/
├─ requirements.txt         # 锁版本
└─ .gitignore               # data/、backup/、logs/、*.db、密钥
~~~

- 代码与数据分离；data/ 不进 git；导出文件不进 git。
- 每个 app 一个 README（表、服务、接口、测试）。
- 决策用 ADR 简短记录（背景/选项/结论/影响），避免以后反复。

### 9.3 每次会话的标准流程

~~~text
1) 开场：读 docs/TASKS.md + 上一个 CHANGELOG；git status 确认干净
2) 让 AI 复述：本任务目标、涉及文件、验收标准、风险点（复述错就纠正）
3) 让 AI 先给计划（≤10 行）+ 需要确认的问题；不直接写代码
4) 确认后：AI 先写/改测试 → 再写实现 → 跑测试
5) 人工看 diff：字段/权限/事务/金额/时间/迁移/安全
6) 跑应用冒烟（启动、页面、关键操作）
7) 更新 CHANGELOG/TASKS；git commit（信息写"做了什么/为什么"）
8) 收尾：记录未做/风险/下次入口
~~~

### 9.4 给 AI 的提示词模板（复制用）

~~~text
【角色】你是本项目开发工程师，遵守 docs/ARCHITECTURE.md 与 docs/DECISIONS.md。
【上下文】项目：<一句话>；本任务：<任务>；相关文件：<路径>；当前分支：<...>
【约束】
- 只改 <文件范围>；不改无关文件；不新增依赖（除非说明理由并等我确认）
- 领域规则先写 pytest；不修改 data/；不写真实数据；不打印密钥
- 数据库变更必须给 migration，并说明回滚方式
【验收】
- <可执行验收标准 1/2/3>
- 运行命令：pytest <...>；启动：python manage.py runserver
【输出】
1) 计划（≤10 行）2) 需要确认的问题 3) 代码 diff 4) 测试结果 5) 风险/未做
先给计划，不要直接写代码。
~~~

### 9.5 防幻觉与防跑偏清单

- **Django/第三方 API**：要求 AI 引用官方文档版本；不确定就让它在代码里加 TODO 并问你，不许编参数。
- **字段/表名**：以 ARCHITECTURE.md 和数据模型为准；AI 编新字段必须先在文档里提案并确认。
- **依赖**：默认只用标准库 + 已锁定依赖；新增依赖要写理由、许可证、体积、是否可离线打包。
- **迁移**：一次迁移只做一件事；不许不可逆删列/改类型；不可逆变更必须单独评审。
- **版本**：Python/Django/HTMX/Bootstrap 全部锁版本；升级单独任务。
- **AI 的"重构"**：默认拒绝；重构必须是独立任务，有测试覆盖。
- **UI 生成**：AI 常把 Bootstrap 类名写错/堆样式；要求先给页面线框与类名约定，再实现。

### 9.6 测试策略（按层）

| 层 | 测什么 | 工具 |
|---|---|---|
| 领域层 | 重量/体积/密度换算、模拟公式、甘特冲突、价格快照 | pytest 纯函数 |
| 服务层 | 收货→入库→出库→盘点、预留、冲销、事务回滚 | pytest-django + 测试库 |
| 接口层 | 权限、状态码、幂等、错误格式、OpenAPI schema | pytest + HTTP client |
| 页面 | 关键页面可打开、表单校验、HTMX 局部刷新、甘特拖动 | 手动/Playwright（可选） |
| 一键 | 干净机启动、升级、断电重启 | 手动清单 |
| 数据 | 余额=流水、金额、批次追溯 | 管理命令 + 对账脚本 |

- 每个黄金用例有编号（T-xxx），失败必须修复或书面接受。
- 不追求覆盖率数字；关键规则必须有正/反/边界/并发用例。

### 9.7 代码评审清单（AI 写完逐条看）

1. 业务规则是否在 domain/服务层，而不是视图/模板？
2. 写操作是否在事务内？库存/流水/审计是否同事务？
3. 金额是否用 Decimal/整数分？有没有 float？
4. 时间是否 UTC 存储、本地显示？有没有 naive datetime？
5. 权限是否服务端校验？有没有只靠隐藏按钮？
6. 幂等/唯一约束/版本检查是否到位？
7. 数据库迁移是否可回滚？有没有删数据风险？
8. 日志是否含敏感信息（密码/token/个人数据）？
9. 有没有 N+1 查询、全表扫描、无分页？
10. 页面是否可用键盘/中文/窄屏？错误提示是否清楚？
11. 测试是否真的跑了？覆盖了失败路径吗？
12. 有没有引入未使用依赖/无关改动/调试代码？

### 9.8 常见坑（本项目高频）

| 坑 | 预防 |
|---|---|
| Windows 中文路径/编码 | pathlib；UTF-8；PowerShell/子进程参数用列表；不要拼字符串路径 |
| SQLite 并发锁 | 单写；短事务；busy_timeout；写重试；不在事务里跑长计算 |
| Decimal vs float | 重量/金额统一 Decimal；数据库存整数分/定点；不用 float 比较 |
| 时区 | 存 UTC；业务日期按本地；Excel 导入解析时明确时区 |
| HTMX 局部刷新 | 返回片段模板；CSRF token 带上；swap 目标明确；错误片段 |
| Django 迁移 | 一次一事；改表前确认可回退；不要手改迁移文件除非明确 |
| 静态/模板打包 | PyInstaller/便携运行时要把 templates/static/migrations 包含；打包后实测 |
| 杀毒误报 | 便携运行时优先；白名单说明；不混淆/不加壳 |
| Excel 导出 | 日期/金额格式、列宽、中文；用 LibreOffice/Excel 双验证 |
| AI 编 API | 锁版本 + 官方文档 + 测试兜底 |

### 9.9 数据与安全

- 开发用合成数据（可生成 seed_demo），不把真实单据/客户/价格贴进 AI 对话。
- 密钥只放环境变量/凭据管理器；代码/文档/git 不含密钥。
- 开发阶段用测试库/合成数据；升级前确认迁移脚本可回退（不做数据备份）。
- Agent token 只存哈希；界面只显示一次；可吊销；调用全审计。

### 9.10 业余时间节奏（建议）

- 每周 2 个会话，每个 3–4 小时；一个会话一个任务；周日晚更新 TASKS/CHANGELOG。
- 每 2 周一个小里程碑，做 15 分钟演示（给自己/用户）；不演示不算完成。
- WIP 限制 1：上一个任务没验收，不开新任务。
- 卡住超过 45 分钟：记录问题、换任务/问 AI 要"最小复现"，不在原地硬耗。

### 9.11 AI 分工

| 角色 | 用途 | 注意 |
|---|---|---|
| 架构/计划 AI | 拆任务、评审方案、写 ADR | 不写代码或只写伪代码 |
| 实现 AI | 按模板写代码+测试 | 必须先给计划；小步 |
| 评审 AI | 按 §9.7 清单挑错 | 最好换一个会话/模型，避免自评 |
| 文档 AI | 把实现写成手册/大白话 | 事实以代码/测试为准 |

### 9.12 风险分级开发流程（避免流程压垮业余时间）

| 级别 | 范围 | 强制动作 |
|---|---|---|
| 高风险 | 库存过账、盘点调整、红冲、迁移、权限、识别结果提交 | 测试先行 + 人工看 diff + 跑相关测试 + 数据对账 + 记录 ADR |
| 中风险 | 模拟公式、甘特冲突、参数版本、导入映射 | 边界测试 + 快照/回归 + 业务验收 |
| 低风险 | 页面排版、说明文字、非业务展示 | 跑页面/相关测试；可简化文档更新 |

> 原则：风险越高流程越重；不允许"所有任务一刀切"，也不允许高风险任务走简化流程。

## 10. 路线图与工期（业余时间）

### 10.1 里程碑（按用户优先级重排）

**二期（M5/M6）**：+9–16 人日，约 +3–6 个月。
**全部**：53–88 人日，约 **8–13 个月**（业余）。不建议对外承诺更短。

### 10.2 建议顺序

1. **M0**（先别写代码）：把过账模型、规则、单据样例、库存粒度、期初/红冲/权限定下来。
2. **M1**：先做出"双击能启动、能登录、能升级"的空壳。
3. **M2**：仓储闭环（最核心）；过账模型先跑通。
4. **M3**：库存报表 + 独立对账脚本（用户能看到价值）。
5. **M4**：识别插件接入（已有插件，只做接口/草稿/审核/人工确认）。
6. **M7**：干净机验收/文档/风险接受。
7. **M5/M6**：生产模拟、甘特原型（二期，按验证结果决定投入）。

### 10.3 成本

- 硬件：0–2,000 元（现有电脑则 0）；UPS 可选 300–600 元。
- 软件：0（不做备份，无云存储费用）。
- 无服务器/域名/备案成本（单机）。

## 13. 给 GPT 的审核清单（本轮重点）

1. **库存过账模型（§5.1.1）**：业务单据/过账事件/流水三层是否闭合？收货不直接加库存、一次过账一次增量、移库一出一入，是否足够防止重复/漏账？
2. **重量流水不变量**：weight_delta_t + 期初建账 + before/after 仅审计，是否解决 P0-2？还需要哪些冲销/精度/并发规则？
3. **磅单与罐测差异**：一次收货一个过账来源（默认磅单）、罐测只作校验/差异，是否成立？待处理/审批流程还缺什么？
4. **生产模拟质量平衡**：输出分类互斥、气体/水可"未纳入质量平衡"，是否能避免虚假精确？首版公式够不够？
5. **无备份升级**：两阶段迁移+不可逆书面接受，是否足够？旧程序/新库版本标识怎么管？
6. **识别插件接入**：插件输出 JSON（或 SQL）→ ingestion API→草稿→人工确认→过账，是否安全？SQL 只解析白名单参数化插入是否可行？去重/证据链够吗？
7. **一期范围**：仓储+报表+识别接入为第一期，生产模拟/甘特二期，是否合理？还能砍什么？
8. **Windows 原生**：便携运行时/启动器/无 WSL/Linux/Docker，还有哪些隐藏依赖与验收项？
9. **单机+预留联网**：认证/URL/附件边界现在留到什么程度才不返工，又不提前加多租户字段？
10. **前后端**：Django 模板+HTMX+Alpine+甘特组件是否合适？API 与 Web 是否重复？
11. **数据模型**：过账事件/流水/库存条目/单据/批次/附件/审计的引用链是否完整？库存粒度唯一键是否正确？
12. **Vibe Coding 风险分级（§9.12）**：对业余+AI 是否可执行？还缺哪些具体护栏（防编字段/假测试/偷改规则）？
13. **测试**：20 组独立对账、并发/重复/部分失败/红冲/混罐/迁移测试，是否足以证明重量账对得上？
14. **工期**：一期 44–72 人日、业余 6–11 个月；二期 8–13 个月，是否现实？哪一步最容易超支？
15. **维护**：一个人+AI 长期维护，30 多张表是否该进一步砍？哪些表可以合并/延后？
16. **风险接受**：无备份、无 Agent 自动过账、甘特只人工，这三项风险用户已接受；还有哪些必须书面披露？
