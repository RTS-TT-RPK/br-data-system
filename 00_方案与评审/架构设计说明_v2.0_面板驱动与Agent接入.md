# 面板驱动的数据接入与管理系统 架构设计说明 v2.0

> 编制：2026-10-27　｜　用途：给 GPT 最终审核，并作为 Vibe Coding 开发基线
> 本文件替代 v1.x 的 ERP 式方案（已归档）。核心变化：不写死业务页面；先做通用样式面板；BR 表格是面板配置；插件/Agent 是数据来源；成分明细拆成可查询行。
> 环境硬约束不变：Windows 10/11 原生运行，不用 WSL/Linux/虚拟机/Docker；不做备份/恢复；金额/重量以单据明细为准。

## 0. 先纠正我此前理解错的地方

| 我之前理解 | 实际产品 |
|---|---|
| 一个固定的仓储/排产 ERP，页面按业务模块写死 | 一个通用的数据面板平台：Excel 表格长什么样，面板就长什么样；面板可配置、可增加 |
| 先定接入契约/字段映射/审核页/去重规则，再开发 | 先做通用面板 + 第一批配置；契约/映射/审核/去重是这平台上的功能，随第一个面板跑通后自然定下来 |
| 生产模拟、甘特排产是核心 | 这些是以后可能加的业务面板/分析，不是第一期；现在不写死 |
| 图像识别只是“一个可选 Agent 功能” | 图像识别插件是主要数据来源；应用的本质是管理、分析、修正这些 AI 提取的数据 |

一句话定位：做一个 Windows 单机应用，把 AI 从各种图片里提取的表格数据接进来，用“像 Excel 一样的可配置面板”管理和分析；人可手动增删改，Agent/插件可通过接口持续送数。

## 1. 产品本质与用户动作

用户日常只做四类动作：

1. 看：打开某个面板（例如“物料库存”“来料分析”“生产记录”），看到和 Excel 一样的一行行数据。
2. 改：手动新增一行、修改格子、删除/作废；成分明细可以拆开编辑。
3. 收：Agent/插件把新识别的数据推过来，系统生成草稿，用户审核确认。
4. 查：按物料/日期/成分/含量等条件筛选、统计、导出；例如“哪些物料含水最高”“某成分含量超过 X 的记录”。

不做（至少第一期）：库存过账/复式记账、生产工单执行、排产优化、财务成本。需要时以后作为“特殊面板/分析”加，不写进底座。

## 2. 从“02_图像识别”工作区学到并要继承的东西

我查看了该工作区的 要看的成果、schemas、插件工作流程_v3.md、tools/导出长表.py，确认这套结构：

### 2.1 宽表：给人看

- 一行 = 一个业务对象（一个样品/一个储罐/一个库位/一次投料）。
- 列 = Excel 表头；成分明细列保留原文，可逐字对图。
- 用于审核、打印、导出、人工核对。

### 2.2 长表：给机器查

facts.jsonl 一行一条事实，字段包括：

~~~text
source_type, source_run_id, source_row_id,
record_date, location, batch_id, container_id, material_name, supplier,
component_standard_name, component_original_name,
numeric_value, unit, raw_value, category
~~~

- 一个数字/一个成分 = 一行；列永远不变，行数增加。
- numeric_value 对百分比已归一（90% → 0.9），unit 写 %，raw_value 保留原文 90%。
- 可直接导入 SQLite，查询/统计不依赖 Excel。

### 2.3 成分明细：一格拆成多行

原图一格：示例溶剂A90% 水5%、PH7

拆成：

| 成分/指标 | 数值 | 单位 | 图上原文 |
|---|---|---|---|
| 示例溶剂A | 90 | % | 示例溶剂A90% |
| 水 | 5 | % | 水5% |
| PH | 7 | — | PH7 |

- 每个成分一行，可单独查询/排序/统计。
- 原文段拼回去必须等于原格原文（空白/顿号/逗号/分号/斜杠不算）；拼不上就拒绝，不猜。
- 名字不是成分的（“杂”“不红”“酸峰”）名字写空，值照录；水/杂等有分类规则，参与合计校验。

### 2.4 可复用的表型契约

schemas/来料分析_v1.json、库存日报_v1.json 已经把“一行代表什么、有哪些列、哪些必填、计量项怎么合计、词表、归档命名”写成了 JSON。这正好可以作为面板定义的种子，不需要重新发明。

### 2.5 对账与审核

- 识别结果先成草稿/宽表，问题记账；人审核后确认。
- 未确认的数据不进正式长表。
- 原图 SHA256 存证，数值与原文两个字段分开保存，谁也不能悄悄改一个。

## 3. 总体架构

### 3.1 单机形态

~~~text
Windows 电脑
┌─────────────────────────────────────────────────────────────┐
│  启动器（tkinter / exe）                                     │
│   启动 waitress → 打开浏览器 → 状态/日志/升级                  │
│                                                             │
│  Django 应用（单进程）                                        │
│   ├─ 面板引擎：读面板定义 → 通用表格/表单/审核页              │
│   ├─ 数据接入：REST API / 文件投递 / MCP（后期）              │
│   ├─ 查询分析：宽表筛选、长表/成分聚合、导出                   │
│   ├─ 面板设计器：新建/复制/改列/改样式（配置，不改代码）        │
│   └─ SQLite（WAL）+ attachments/ + logs/                    │
└─────────────────────────────────────────────────────────────┘
~~~

### 3.2 技术栈（保持 Windows 原生）

| 层 | 选型 | 说明 |
|---|---|---|
| 运行 | Windows 10/11 64 位原生 | 不用 WSL/Linux/虚拟机/Docker/Cygwin |
| Python | 3.13 64 位（便携运行时） | 不要求用户装 Python |
| Web | Django 5.2 LTS | 模板、ORM、迁移、权限、表单 |
| API | Django Ninja | JSON 接口、OpenAPI、给插件/Agent 用 |
| DB | SQLite 3（WAL） | 单机；JSON1 查 data_json；金额/数值用定点 |
| 前端 | Django 模板 + HTMX + Alpine + Bootstrap（本地静态） | 不引入 Node 构建 |
| Excel | openpyxl | 导入/导出 .xlsx |
| 启动器 | tkinter | 标准库 |

### 3.3 分层

~~~text
接口层：面板页面 / REST API / 文件投递
应用层：面板服务、记录服务、接入服务、查询服务、面板设计服务
领域层：面板定义校验、成分拆分/对账、数值归一、去重规则、样式解析
数据层：panel_definition / record / record_reading / record_component / ...
~~~

关键原则：页面不写死列名。所有列、表单、导出、校验都从面板定义读取；加一个新面板 = 加一份配置 + 必要时加一个特殊单元格渲染器，不改路由/页面。

## 4. 核心概念与数据模型

### 4.1 概念

| 概念 | 大白话 | 说明 |
|---|---|---|
| 样式（Style） | 这张表长什么样 | 边框、表头颜色、行高、字体、冻结列、数字格式、是否斑马纹 |
| 面板（Panel） | 一张可打开的表 | 绑定样式 + 列定义 + 数据 + 操作；例如“物料库存”“来料分析” |
| 面板定义（Panel Definition） | 这张表的图纸 | 列、类型、必填、宽度、分组、表单布局、校验、权限、操作 |
| 记录（Record） | 面板里的一行 | 宽表数据存 data_json；保留来源、状态、版本 |
| 读数（Reading） | 一行里的一个数 | 例如液位、密度、使用率；一条一行，便于查询 |
| 成分（Component） | 成分明细拆出来的一行 | 成分名/原文名/数值/单位/原文/分类 |
| 接入批次（Ingestion） | 插件/Agent 送来的一批数据 | 原始 payload、问题、审核状态、来源图 |
| 面板实例版本 | 面板定义改过几版 | 旧记录保留旧版本，避免改列后历史数据错位 |

### 4.2 数据表（约 12 张，先小后大）

| 表 | 关键字段 | 用途 |
|---|---|---|
| panel_style | id, key, name, config_json | 样式预设（br_table / image_review / generic） |
| panel_definition | id, key, name, row_unit, style_id, columns_json, measurements_json, form_layout_json, actions_json, permissions_json, version, status | 面板图纸；可复制/改版/发布 |
| record | id, panel_key, panel_version, data_json, source_type（manual/agent/plugin/import）, source_run_id, source_row_id, status（draft/confirmed/void/deleted）, image_id, confidence, created_by, created_at, updated_at, version | 宽表一行 |
| record_reading | id, record_id, field_key, name, numeric_value, unit, raw_text, category, confidence | 一行里的普通数值（液位/密度/使用率等） |
| record_component | id, record_id, field_key, component_std, component_original, numeric_value, unit, raw_text, category（comp/water/misc/other）, confidence, material_id | 成分明细拆行 |
| ingestion_batch | id, panel_key, source_type, source_run_id, image_sha256, payload_json, issues_json, status, created_at | 插件/Agent 一次送数 |
| ingestion_row | id, batch_id, row_key, raw_json, mapped_json, status, issues_json | 批次里的每一行 |
| attachment | id, sha256, filename, mime, size, path, source, uploaded_by, created_at | 原图/附件（按内容寻址） |
| component_alias | id, alias, standard_name, category, note | 成分别名（对照表） |
| saved_view | id, panel_key, name, filters_json, columns_json, sort_json | 保存的查询视图 |
| operation_log | id, actor_type, actor_id, action, entity_type, entity_id, before_json, after_json, at, request_id | 审计 |
| app_setting | key, value_json | 配置（默认样式、去重键、保留策略） |

说明：不建 30+ 张业务表。业务表 = 面板配置 + 记录；以后真需要库存过账/工单，再作为专门模块加，不污染底座。

### 4.3 记录与长表的关系

~~~text
record（宽表一行）
  ├─ data_json：原样保留这一行所有列（含成分明细原文）
  ├─ record_reading：这一行里可比较的数（液位/密度/使用率/数量…）
  └─ record_component：这一行成分明细拆出的每个成分
~~~

- 宽表用于显示/编辑/导出；长表用于查询/统计。
- 两者由同一份数据生成，不能各写一套；保存/提交时同时落。
- 旧记录用 panel_version 保留当时的列定义；面板改版不破坏历史。

## 5. 通用样式面板（本次重点）

### 5.1 面板定义长什么样（示例）

~~~json
{
  "key": "br_material_property",
  "name": "物料性质",
  "row_unit": "一行 = 一个物料",
  "style": "br_table",
  "columns": [
    {"key": "name_cn", "label": "中文名", "type": "text", "required": true, "width": 160, "group": "基本信息"},
    {"key": "name_en", "label": "英文名/缩写", "type": "text", "width": 140},
    {"key": "cas_no", "label": "CAS号", "type": "text", "width": 120},
    {"key": "density", "label": "密度(g/mL)", "type": "number", "decimals": 4, "width": 110},
    {"key": "boiling_point", "label": "沸点(℃)", "type": "number", "decimals": 1, "width": 100},
    {"key": "components", "label": "成分明细", "type": "components", "width": 320}
  ],
  "measurements": {
    "enabled": true,
    "unit": "%",
    "sum_max": 100.0,
    "categories": {"water": "never", "misc": "if_present", "default": "always"}
  },
  "form_layout": [["name_cn", "name_en", "cas_no"], ["density", "boiling_point"], ["components"]],
  "actions": ["create", "edit", "delete", "export", "import"],
  "permissions": {"view": ["viewer", "editor", "admin"], "edit": ["editor", "admin"]}
}
~~~

- 列类型：text / number / date / percent / identifier / components / image / badge。
- components 类型的列自动显示拆分后的成分数、合计值、异常标记。
- 表单布局按 group/行配置；不写模板。
- 权限按动作配置；服务端校验。

### 5.2 样式预设

| 样式 key | 用途 | 视觉 |
|---|---|---|
| br_table | BR 数据系统的表格风格 | 细边框、表头浅色、紧凑行高、冻结首列、斑马纹、数字右对齐 |
| image_review | 识别审核页 | 宽表 + 低置信度标黄 + 问题列 + 原图侧栏 |
| generic | 通用 | 简洁、留白、适合新面板 |

样式是配置（颜色/边框/密度/字体/列宽/数字格式），不是另写 CSS 页面；以后加样式只加配置。

### 5.3 第一批面板（种子配置，不是写死代码）

BR 数据系统的 9 张表（来自现有工作簿）：

1. 物料性质基础数据库（15 列）
2. 共沸数据（7 列）
3. 储存位置定义（4 列）
4. 储罐类型液位体积（11 列）
5. 五金配件库（8 列）
6. 物料库存（12 列，含成分明细）
7. 操作日志（10 列）
8. 车间投料工艺卡记录（12 列，含成分明细）
9. 车间生产记录（10 列）

图像识别工作区的表型：

- 来料分析（日期/位置/物料/批次/桶号/厂商/成分）
- 库存日报（日期/位置/物料/读数/成分）
- 其他在 schemas/ 里注册过的表型（按实际增加）

这些都以 seeds/panels/*.json + seeds/styles/*.json 形式存在；开发只写读取和渲染，不为每张表写页面。

### 5.4 面板设计器（配置，不改代码）

用户可以：

1. 新建面板：选样式 → 加列（名称/类型/必填/宽度/分组）→ 配表单布局 → 配操作/权限 → 预览 → 发布。
2. 复制现有面板（例如复制“物料库存”改成“来料分析”）。
3. 导入/导出面板定义 JSON（换电脑/备份配置；注意不是数据备份）。
4. 改版：已发布面板改列时生成新版本；旧记录保留旧版本显示。

开发阶段不写死任何具体表：先内置 2–3 个样例面板证明引擎，其他用设计器加。

### 5.5 通用表格页

一个路由 /p/<panel_key> 渲染所有面板：

- 顶部：面板名、行数、筛选、搜索、列选择、导出、新增。
- 表格：按 columns 渲染；支持排序/分页/冻结/行高亮；成分列显示摘要。
- 行操作：编辑、复制、删除/作废、查看原图（若有）。
- 批量：选中导出/删除/审核。
- 表单页 /p/<panel_key>/new 与 /p/<panel_key>/<id>：按 form_layout 渲染；成分编辑器可增删行、粘贴拆开。
- 审核页 /p/<panel_key>/review/<batch_id>：左原图右宽表，问题清单，逐行通过/修改/拒绝。

## 6. 成分明细与长表结构（可拆分查询）

### 6.1 保存结构

~~~text
record:
  id=1001, panel_key=br_inventory,
  data_json={
    "储位":"示例库区1#", "物料":"示例溶剂A", "成分明细":"示例溶剂A90% 水5%、PH7",
    "液位":4.33, "密度":0.7880, "使用率":"65%"
  }

record_reading:
  (record_id=1001, name="液位", numeric_value=4.33, unit="吨", raw_text="4.33")
  (record_id=1001, name="密度", numeric_value=0.7880, unit="—", raw_text="0.7880")
  (record_id=1001, name="使用率", numeric_value=65, unit="%", raw_text="65%")

record_component:
  (record_id=1001, component_std="示例溶剂A", component_original="示例溶剂A", numeric_value=0.9, unit="%", raw_text="示例溶剂A90%", category="comp")
  (record_id=1001, component_std="水", component_original="水", numeric_value=0.05, unit="%", raw_text="水5%", category="water")
  (record_id=1001, component_std="PH", component_original="PH", numeric_value=7, unit="—", raw_text="PH7", category="other")

规则：
- 百分比 numeric_value 存小数（0.9），显示时 ×100；unit="%"；非百分比（PH）存原值，unit="—"。
- raw_text 保留图上原文；data_json 里保留整格原文。
- 分类：comp=成分，water=水，misc=杂/其他，other=指标（PH 等）。
- 合计校验：按面板 measurements 配置（水不计、杂有值才计、默认计），超过 sum_max 报问题；不自动改数。
- 拆分对账：所有 raw_text 按顺序拼接必须等于原格原文（忽略空白/顿号/逗号/分号/斜杠）；不通过则拒绝写入，标问题。
- 手工编辑：可增删改成分行；保存时重算合计与对账；保留修改前后值到审计。

### 6.2 可查询的例子

| 问题 | 查询 |
|---|---|
| 哪些物料含水最高？ | record_component where category=water order by numeric_value desc |
| 某成分含量超过 5% 的记录？ | component_std = ? and numeric_value > 0.05 |
| 每个物料的主要成分是什么？ | group by record/material, order by numeric_value desc |
| 来料分析的成分分布？ | join record + component where panel_key=incoming_analysis |
| 某批次/日期范围的所有读数？ | record_reading join record where date between ... |
| 成分合计异常的面板行？ | per record sum(category != water) vs sum_max |

### 6.3 导入/导出

- 导入 Excel：按面板 columns 映射；成分列支持“整格原文”或“已拆分行”两种；拆不开的进问题清单。
- 导出宽表：一行一行，成分列原文（给业务看）。
- 导出长表：一行一个成分/读数（给分析/迁移用），列与 facts.jsonl 对齐。
- 导出面板定义：JSON（配置，不是数据）。

## 7. Agent / 插件接入（数据来源）

### 7.1 推荐方式：JSON 推送（不是执行 SQL）

插件/Agent 调：

~~~http
POST /api/v1/ingestions
Content-Type: application/json

{
  "panel_key": "incoming_analysis",
  "source": {
    "type": "dsh_plugin",
    "run_id": "20990101_001",
    "image_sha256": "...",
    "image_path": "inbox/IMG_001.jpg"
  },
  "document_type": "来料分析",
  "rows": [
    {
      "row_key": "R001",
      "fields": {"日期":"2026-10-27","位置":"示例库区1#","物料":"示例溶剂A","批次":"DEMO-001","桶号":"D01","厂商":"示例供应商"},
      "components": [
        {"name":"示例溶剂A","raw_value":"90%"},
        {"name":"水","raw_value":"5%"},
        {"name":"PH","raw_value":"7"}
      ],
      "readings": [
        {"name":"液位","raw_value":"4.33","unit":"吨"}
      ],
      "uncertain": [],
      "confidence": 0.93
    }
  ]
}
~~~

应用处理：

1. 找面板定义，校验列/必填/类型/单位；
2. 成分拆分/对账/归一（90% → 0.9）；
3. 去重（图片 SHA256 + 业务键 + 行内容哈希）；
4. 生成 ingestion_batch + 每行 draft（不直接进正式记录）；
5. 审核页：左原图右宽表，问题清单；人通过/修改/拒绝；
6. 通过后写 record + record_reading + record_component，状态 confirmed，写审计；
7. 返回结果：接收行数、问题数、草稿 id。

### 7.2 如果插件现在输出的是 SQL

不执行 SQL。两种安全适配：

1. 推荐：插件/中间层把 SQL 查询结果转成上面的 JSON。SQL 是按某套表结构写的，我们的面板结构不同，本来也不能直接跑。
2. 兼容：应用侧加一个 sql_adapter，只解析 INSERT INTO <白名单表> VALUES (...)，把值转成 JSON，再走同一校验；禁止 UPDATE/DELETE/DDL/多语句/任意函数。解析失败进问题清单，不静默跳过。

结论：能“直接注入”，但注入的是结构化数据，不是可执行 SQL。这样才不会绕过校验/权限/审计。

### 7.3 其他接入方式

| 方式 | 用途 |
|---|---|
| HTTP API | 插件/Agent 在线推送（主方式） |
| 文件投递 | 插件落 inbox/*.json，应用扫描导入（离线/批处理） |
| Excel/CSV 导入 | 人工补录/历史数据 |
| MCP | 后期给 Agent 提供工具：列面板、查记录、建草稿、查成分；提交仍需人工确认 |

### 7.4 审核与去重（先默认后配置）

- 默认去重：image_sha256 + panel_key + 行内容哈希；重复批次直接拒绝/提示。
- 业务级去重：面板定义里可选配 dedupe_keys（如日期+位置+物料+批次）；第一版先做“疑似重复提示”，人工决定。
- 审核页必须显示：原图、识别置信度、问题字段、修改前后值、谁确认。
- 未确认的草稿不进正式查询/导出。

## 10. Vibe Coding 开发规范（针对“配置驱动”）

### 10.1 铁律

1. 先做引擎，再做面板：不为任何一张具体表写专用页面/路由。
2. 配置与代码分离：面板定义、样式、种子数据放 seeds/，代码只读配置。
3. 一个面板定义 schema：列/校验/表单布局/权限都走同一份 JSON；先写 schema 测试。
4. 小步：一次只做一个能力（列表→表单→成分→接入→审核），每步可演示。
5. AI 不许写死列名：发现代码里出现具体列名（除种子配置/测试）就退回。
6. 测试：渲染器用样例面板；成分拆分/对账/合计用黄金用例；接入用样例 payload。
7. 数据安全：真实数据不进 AI 对话；开发用合成数据。
8. 文档：PROJECT/ARCHITECTURE/DECISIONS/TASKS/CHANGELOG 五份；只更新受影响的。
9. 风险分级：成分归一/对账、接入提交、权限/迁移必须测试先行；纯样式可简化。
10. 可回退：每次提交前 git；数据库结构变更给迁移；不删旧字段。

### 10.2 每次会话流程

- 读 TASKS + 当前面板配置；确认本任务只动引擎/一个面板；
- AI 先复述目标 + 影响的文件 + 验收；
- 先写/改测试（渲染器用样例配置；成分用黄金片段）；
- 实现；跑测试；打开页面看；
- 人工看 diff；更新 CHANGELOG；提交。

### 10.3 常见坑

- 把面板配置写成 Python 常量/模板 if-else → 必须走 JSON。
- 改面板列后旧记录错位 → 记录 panel_version + data_json 缺列显示空。
- 百分比存 90 还是 0.9 → 统一存小数，显示乘 100；导入导出明确。
- 成分拆开原文拼不上 → 拒绝并报问题，不猜。
- 删除记录 → 软删除/作废 + 审计；物理删除仅管理员。
- 静态资源/模板打包 → 便携运行时要包含 templates/static/seeds；打包后实测。
- Windows 中文路径 → pathlib + UTF-8。

## 12. 风险

| 风险 | 缓解 |
|---|---|
| 面板配置过度灵活，变成“低代码平台”做不完 | 只做表格/表单/审核/查询四类；列类型先 6 种；不做公式/流程引擎 |
| 成分数据质量（AI 识别错/漏） | 原文对账 + 合计校验 + 人工审核 + 置信度标记 |
| 插件输出格式变 | 接入层做适配器；先冻结一个 JSON 样例；SQL 只解析白名单 INSERT |
| 面板改版破坏历史 | panel_version + data_json；旧记录只读旧版 |
| 记录量变大后 SQLite 查询慢 | 长表索引（panel_key, component_std, date）；分页；必要时物化视图 |
| 用户不会配面板 | 先内置种子 + 复制；设计器只暴露常用项 |
| Vibe Coding 跑偏 | 配置/代码分离、schema 测试、AI 不得写死列名 |
| 无备份 | 用户已接受；导出 Excel/长表作为人工留档 |
